# 26 · 时延测量与压测

> 一句话：时延不是"一个数"，是**一条链路上每一跳的预算之和**。测不出"哪一跳慢"，
> 就只会得到"有时候快有时候慢"这种没法优化的结论。

---

## 一、通用知识

### 1.1 为什么不用平均值

```
样本：10ms, 11ms, 12ms, 13ms, 900ms
平均：189ms     ← 看起来"还行"
P50 ：12ms      ← 大多数人体验
P99 ：900ms     ← 少数人体验极差
```

平均值被长尾拉高，又掩盖了长尾。对外说"平均 189ms"、用户体验"有时候卡一秒"，
两边都没说谎，但都没用。

| 分位 | 用途 |
| --- | --- |
| P50 | 典型体验 |
| P95 | 常规上限（SLO 常用） |
| P99 | 长尾（用户投诉来自这里） |
| MAX | 排查异常点（不适合做 SLO） |

### 1.2 三种测量方式

| 方式 | 做法 | 误差来源 |
| --- | --- | --- |
| **探针** | 发一条带唯一标记的数据，轮询下游何时出现 | 轮询间隔（精度上限） |
| **埋点** | 在代码里记录时间戳 | 时钟、采样 |
| **端到端** | 改数据 → 看界面变化 | 界面刷新周期 |

本项目的三种都用：

- `check_lag.py`：探针（发事件 → 查 Doris）
- `demo-change.sh`：端到端（改 MySQL → 查 DWS/ADS）
- `p7-acceptance.sh`：端到端 + 界面（查 API）

### 1.3 固定开销必须先扣掉

```bash
time docker exec rt-doris-fe mysql -e "SELECT 1"
# real 0m0.826s     ← 查询本身不到 1ms
```

`docker exec` 的 826ms 是：CLI 启动 + API 调用 + 容器内 fork + 连接认证。
如果不扣掉，你会得出"查询要 0.8 秒"的错误结论。

两种处理：

- **常驻连接**（本项目做法，见 `23`）—— 把固定开销降到一次
- **测基线再相减** —— 简单但只适用于粗测

### 1.4 测量本身的误差

| 误差来源 | 影响 | 处理 |
| --- | --- | --- |
| 轮询间隔 | 精度上限 = 间隔 | 用 200ms 而非 1s |
| 时钟不同步 | 跨机器测量偏 | 同一台机器取时间 |
| 观察者效应 | 频繁查询拖慢系统 | 采样而非全量 |
| 缓存/预热 | 第一次特别慢 | 丢弃前几次，或单独报告 |

### 1.5 端到端拆账

```
总延迟 4s
  ├─ 源端检测（CDC 读 binlog）      ? ms
  ├─ 计算（算子处理）                 ? ms
  ├─ 攒批（等 checkpoint / flush）    最多 10s
  ├─ 写目标（Stream Load）            ? ms
  ├─ 物化（ADS 刷新）                最多 60s
  └─ 展示（前端轮询）                最多 1.5s
```

**不拆账就无法优化** —— 你只知道"慢"，不知道"哪一段慢"。
拆完之后通常会发现：**最大的那一段是"等"，不是"算"**。

### 1.6 压测的三个参数

```
速率（每秒多少条）
时长（跑多久）
样本量（够不够算 P99）
```

P99 需要至少 100 个样本才有一点意义（严格说要 1000+）。
本项目 `check_lag.py` 取 200 条样本，P99 实际是"第 2 慢的那条"，只能当量级参考。

### 1.7 失败必须显式失败

```bash
# ❌ 失败被当成"命中"
API_GMV() { curl -s ... || echo "ERR"; }
[[ "$api" != "$baseline" ]] && echo "可见 306ms"

# ✅
curl -f || continue                 # 失败跳过这一轮，不计入统计
[[ "$api" =~ ^[0-9.]+$ ]] || continue
```

本项目早期版本在接口全程 500 的情况下，也能打印出一份漂亮的验收报告并 `exit 0`。

## 二、在本项目中

### 2.1 `check_lag.py`：探针 + 常驻管道

```
① 生成一条带唯一 event_id 的事件，发到 Kafka，记 t0
② 轮询 ods_user_event 直到它出现，记 t1 → ODS 延迟
③ 轮询 dwd_user_event_clean 直到它出现，记 t2 → DWD 延迟
④ 重复 200 次，算 P50 / P95 / P99
```

实测（200 条样本）：

| 段 | P50 | P99 |
| --- | --- | --- |
| Kafka → ODS（04 作业） | 5,247ms | 9,932ms |
| ODS → DWD（06 作业） | 5,132ms | 10,035ms |

为什么是"5 秒级"而不是"毫秒级"：**探针要等 checkpoint**（10s 间隔）。
这不是链路慢，是"可见延迟"的下限由 checkpoint 决定（见 `17`）。

### 2.2 `demo-change.sh`：改一行 MySQL，量到三个位置

```
① 僵尸自检：四个源没读满 40 万行 → 直接退出，不碰数据
② 记下原值，UPDATE 一行（+delta）
③ 轮询 dws_trade_overview_1m → 记 DWS 可见时间
④ 轮询 ads_realtime_overview → 记 ADS 可见时间
⑤ 查大屏 API → 记面板可见时间
⑥ trap EXIT 回滚原值
```

实测：

| 位置 | 耗时 |
| --- | --- |
| DWS | 1.4 ~ 4.2s |
| ADS | 10.7 ~ 56.4s |
| 面板 | ≈ ADS + 1.2s |

**ADS 的区间为什么这么宽**：它等的是 60 秒批刷的相位。改的瞬间如果刚过批刷点，
就要等满 60 秒；如果刚好赶上，10 秒就够。

这不是"不稳定"，是**采样相位问题**。报数时必须说清：

```
"ADS 可见 10.7~56.4s（60s 批刷相位）"
```

### 2.3 四个数字，四种口径

同一句"改一行 MySQL → 大屏可见"，项目文档里出现过四个数：

| 数字 | 出处 | 口径 |
| --- | --- | --- |
| 0.24 ~ 3.1s | README | P7 验收，**主动触发** ADS 刷新 |
| 0.29 ~ 4.02s | `docs/01` | 同上，另一轮采样 |
| 294 ~ 4,019ms | `docs/05` | 同上，13 轮验收的 min~max |
| **17.3s / 60.7s** | `docs/03` | **不触发**，等 60s 批刷周期的真实等待 |

前三个是"触发刷新后多快可见"，第四个是"什么都不做，自然等待多久"。
**两个都对，但必须说清是哪个** —— 不标口径，面试一追就露。

现在文档统一成：

```
P7 主动触发 ADS 刷新：294 ~ 4,019ms
等 60s 批刷周期：     17.3 ~ 60.7s
```

### 2.4 `p7-acceptance.sh`：13 轮验收

```
13 轮，每轮：改一行 MySQL → 等面板变化 → 记时间
结果：237 ~ 3,086ms
```

脚本自己判 PASS/FAIL 并返回退出码（0/1/2），可以直接挂 CI。

它修过的最重要的 bug 是"失败伪装成成功"（见 1.7）：
旧版本 `API_GMV() { curl ... || echo "ERR"; }` + `[[ "$api" != "$b_api" ]]`，
接口 500 时 `ERR != "110.00"` → 立刻记成"可见 306ms"且 `exit 0`。

### 2.5 一次静默降级：`e2e_latency_ms` 长期是常量

```
现象：从大屏调用健康度采集时，e2e_latency_ms 永远是 3849
     人工在终端跑同一个脚本，正常
原因：大屏侧用 MSYS_NO_PATHCONV=1 包住了子进程
     → 关掉了 POSIX → Windows 路径翻译
     → python -c 打不开 /d/Users/.../latency.json
     → FileNotFoundError 被 2>/dev/null 吞掉
     → 变量为空 → 走了默认值 3849（早期硬编码的基线）
修法：改用 sed 读 JSON，不起解释器
```

这条的教训：**"从某个入口调用时才对"的 bug，一定在环境差异里**（PATH、编码、路径、
工作目录）。而且 `2>/dev/null` 会让它变成"没有报错"。

换 sed 后又暴露一个：`[[ 10034.6 -le 0 ]]` 在 bash 里报
`invalid arithmetic operator` —— Bash 只算整数，浮点要先 `awk` 取整。

### 2.6 测量脚本的自检清单

```
□ 失败是否显式失败（不是"不等于基线就算命中"）
□ 固定开销是否扣除（docker exec 826ms）
□ 轮询间隔是否小于预期延迟的 1/3
□ 样本量是否够算 P99（≥100）
□ 是否报告 min/max 而不是只报平均
□ 是否标明"是否触发了额外的刷新"
□ 是否清理了测试数据（trap EXIT）
□ 是否有僵尸自检（避免测一个不工作的系统）
```

最后一条是本项目特有的：`demo-change.sh` 第 0 步检查
`overview_join_rows ≥ 40 万`，不满足就退出 —— **在僵尸作业上测时延毫无意义**。

## 三、速查

```bash
# 探针测量（200 条样本）
python scripts/check_lag.py --samples 200

# 端到端（含僵尸自检与自动回滚）
bash scripts/demo-change.sh --delta 500

# 验收（13 轮，自己判 PASS/FAIL）
bash dashboard/p7-acceptance.sh
echo "exit=$?"        # 0=PASS 1=FAIL 2=环境问题
```

| 要报的数 | 必带的口径 |
| --- | --- |
| "改一行 MySQL → 大屏" | 是否主动触发 ADS 刷新 |
| "端到端延迟" | 从哪到哪（源→ODS？源→DWD？源→面板？） |
| "P99" | 样本量与采样窗口 |
| "DWS 延迟" | 是否含 checkpoint 等待（10s） |

| 症状 | 原因 |
| --- | --- |
| 延迟数永远一样 | 静默降级到硬编码常量 |
| 验收报告很漂亮但系统是坏的 | 失败被当成命中 |
| 查询显示 800ms+ | 没扣 `docker exec` 固定开销 |
| ADS 延迟在 10s 和 60s 之间跳 | 采样相位，不是不稳定 |
| `invalid arithmetic operator` | Bash 只算整数，浮点先 `awk` |
