# 20 · 指标口径设计

> 一句话：口径不是"这个数怎么算"，而是**"这个数在什么前提下可以被相加、被比较、被追溯"**。
> 大部分数据吵架不是因为算错，是因为两个人算的不是同一个东西。

---

## 一、通用知识

### 1.1 指标的三个层次

| 层次 | 定义 | 例子 |
| --- | --- | --- |
| **原子指标** | 一个业务动作 + 一个度量 | 订单金额、订单笔数、事件次数 |
| **派生指标** | 原子 + 修饰（时间/维度/过滤） | 近 7 天已支付订单金额 |
| **复合指标** | 多个派生指标运算 | 客单价 = 金额 / 笔数 |

复合指标最容易出问题：分子分母的**时间窗口、过滤条件、粒度**必须完全一致。

### 1.2 可加性：一切错误的根源

| 类型 | 定义 | 例子 | 能否跨维度 SUM |
| --- | --- | --- | --- |
| **可加** | 任何维度切片相加都等于总体 | 金额、件数 | ✅ |
| **半可加** | 某些维度可加，某些不可 | 库存（可跨商品，不可跨时间） | ⚠️ |
| **不可加** | 相加没有意义 | 比率、UV、去重计数 | ❌ |

三条铁律：

**① 比率不能相加，也不能再平均**

```
正确：SUM(迟到单数) / SUM(已妥投单数)
错误：AVG(各州迟到率)
```

后者是"平均的平均"，会被小样本州严重带偏。

**② 去重计数跨维度不可加**

```
北京 100 个买家 + 上海 100 个买家 ≠ 200 个买家
（有人在两地都买过）
```

**③ 累计值不能 SUM**

```
每日累计 GMV 曲线：day1=10, day2=25, day3=45
SUM = 80  ← 毫无意义（把累计当增量）
```

### 1.3 分母：比分子更容易错

比率的分子通常直观，分母才是坑：

| 指标 | 分子 | 分母该是什么 | 常见错误 |
| --- | --- | --- | --- |
| 迟到率 | 迟到单数 | **已妥投**单数 | 用全部订单（含未发货） |
| 转化率 | 支付人数 | 进入漏斗的人数 | 用"访问 UV"（不同集合） |
| 退款率 | 退款单数 | 支付单数 | 用下单单数 |
| 毛利率 | 毛利 | 营收 | 用含税/不含税混算 |

**分母错了通常不会报错，只会让数字"看起来合理但偏一点"。**

### 1.4 过滤器与累计值

```sql
-- 错误：WHERE 过滤会让"累计"随时间倒退
SELECT dt, SUM(price) FROM orders
WHERE order_status <> 'canceled'
GROUP BY dt;
```

如果口径是"累计 GMV"，加任何 `WHERE` 都会让历史某天的值变小 ——
因为后来被取消的订单会从历史里消失。**累计型指标必须"全量收下 + 单独的无效金额列"**。

### 1.5 时间口径

| 口径 | 含义 | 陷阱 |
| --- | --- | --- |
| 自然日 `dt` | 按业务日期切 | 跨时区时"今天"是哪天 |
| 滚动窗口 | 最近 24 小时 | 与自然日不可比 |
| 累计 | 从起点到当前 | 不能 SUM，不能同比 |

同一个指标"今日 GMV"和"近 24 小时 GMV"是两个指标，名字必须区分。

### 1.6 一份口径文档该写什么

```
名称：      净 GMV
定义：      GMV − 无效交易金额
分子/分母：  SUM(item_total) − SUM(item_total WHERE status IN (...))
粒度：      订单行 → 聚合到订单
时间：      按 order_purchase_timestamp 的自然日
已知偏差：  不含 775 个无明细订单（162,591.95）
SQL：      见 sql/doris/07-ads.sql 第 N 行
负责人/变更：2026-11-03 从 SUM(price) 改为 SUM(item_total)
```

最后一行最重要：**口径会变，变更必须有记录**。否则半年后没人知道为什么两个报表差 200 万。

### 1.7 展示口径与计算口径

大屏上写"今日成交 ¥xxx"，这个数字的口径必须能被点开看到。
本项目在界面上直接标注了数据来源与截止时间（见 [24](24-原生-JS-与-SVG-可视化.md)），因为
**"看起来像实时"和"是实时"是两件事**。

## 二、在本项目中

### 2.1 GMV：一次被推翻的口径

| | 旧口径 | 现口径 |
| --- | --- | --- |
| 表达式 | `SUM(price)` | **`SUM(item_total)`** |
| 数值 | 13,494,400.74 | **15,843,553.24** |
| 含运费 | ❌ | ✅ |
| 剔除取消 | ✅（`WHERE`） | ❌（不剔，另设列） |

为什么推翻：

```
WHERE order_status <> 'canceled' 会让历史某天的 GMV 在订单被取消后变小
→ 累计曲线出现"倒退"
→ 而这条曲线是大屏的核心视觉
```

新口径：**全量收下**，另设 `canceled_gmv` 列单独统计（108,026.21，占 0.68%，467 单）。
净 GMV 在查询时相减，不落表：

```sql
SELECT gmv - canceled_gmv AS net_gmv FROM ads_realtime_overview;
```

好处：两个数都在，随时能对账；坏处：看板上必须标清是哪个。

### 2.2 支付金额 ≠ GMV（差 16.5 万）

```
GMV（订单行金额合计）     15,843,553.24
支付流水合计              16,008,872.12
差额                        165,318.88
```

差额拆解：

| 来源 | 金额 |
| --- | --- |
| 775 个订单有支付但无订单明细 | 162,591.95 |
| 天然偏差（分期、手续费、部分支付） | 2,726.93 |

这不是"算错了"，是**两个数据集的覆盖范围不同**。
如果强行让它们相等，就必须丢掉那 775 单 —— 那是篡改数据。

**正确做法：两个指标都保留，并在口径文档里写清差额来源。**

### 2.3 买家数与订单数：四套口径

| 指标 | 值 | 口径 |
| --- | --- | --- |
| `order_cnt`（DWD 去重） | **98,666** | `COUNT(DISTINCT order_id)` |
| `order_cnt`（含无明细订单） | 99,470 | 从 `orders` 表算 |
| `order_cnt`（含非法状态） | 100,010 | 未过滤 |
| `order_cnt`（原始行） | 101,686 | 含重复 |

**四个都对，取决于问什么。** 对外只说一个，其他三个写进口径文档作为对照。

买家数同理：

```
各州买家数之和      97,734
全国去重买家数      95,420
差 2,314            因为有 37 人在两个州下过单（跨州重复计数）
```

**跨维度不可加**这条在这里是具体数字，不是抽象原则。

### 2.4 迟到率：三态与两个分母

`is_late` 有三个值：

| 值 | 含义 | 行数 |
| --- | --- | --- |
| 1 | 迟到 | 8,715 |
| 0 | 准时 | 101,481 |
| **NULL** | 未妥投（还在路上/丢了） | 2,454 |

```
正确：8,715 / 110,196 = 7.91%     （分母 = 已妥投）
错误：8,715 / 112,650 = 7.74%     （把未妥投算进分母）
```

而"订单级迟到率"是 **8.11%** —— 也对，因为一个订单只要有一行迟到就算迟到，
分子分母同时变小。两个指标名字必须区分：**行级 / 订单级**。

### 2.5 `cum_gmv` 不能 SUM

`ads_realtime_overview` 里有一列 `cum_gmv`（当日累计）。它长这样：

```
minute   gmv    cum_gmv
00:01    100    100
00:02    150    250
00:03    120    370
```

`SUM(cum_gmv)` = **14.49 亿**，是总 GMV 的 **91.5 倍**。
它只能取 `MAX(cum_gmv) WHERE dt = 今天`，或者直接读最后一分钟的行。

### 2.6 漏斗：人次口径，不是会话

```
口径：同一用户同一商品，分别计入各自环节
不要求"看了 A 才能加购 A"，但要求"加购 A 的人里有多少人之前看过 A"
```

为什么不按会话：真实电商里"看了 A 加购了 B"是常态，按会话算不出同商品转化。
按"用户 × 商品"算，每一步的分母都是"该商品的曝光人数"。

这个选择直接决定了埋点生成器的设计（见 [22](22-Python-工程.md) 的第三条原则）。

### 2.7 比率列的小数误差

17 个州的 `gmv_ratio` 各留 4 位小数，相加：

```
理论        1.0000
实测        0.9997 ~ 1.0004
最大误差    0.00085
```

所以验收判据不能用 `SUM(ratio) = 1.0000`，要用 `ROUND(SUM(ratio), 3) = 1.000`。

**这类"精度导致的判据失败"会浪费很多时间**，因为看起来像数据错了。

### 2.8 口径要写在界面上

大屏顶栏标注：

```
今日成交  暂无  [CDC]
交易日    2017-11-24
```

漏斗面板底部两行脚注：

```
行为流口径：「支付」= 上报 pay 事件的人次
不写订单表、不产生 GMV，与下方交易面板非同源
```

因为这两块数据来自**两条完全不同的链路、两套时间轴**：

| | 交易面板 | 漏斗面板 |
| --- | --- | --- |
| 数据源 | MySQL binlog（2016~2018 历史） | Kafka 埋点（今天） |
| 时间轴 | 2017-11-24 | 2026-11-04 |
| 是否会变 | 只有改 MySQL 才变 | 持续在变 |

不标注，看的人一定会问"为什么漏斗在动，GMV 不动"（见 [24](24-原生-JS-与-SVG-可视化.md) 的实战）。

## 三、速查

### 口径自检清单

```
□ 一行代表什么？（粒度）
□ 分子、分母分别是什么？分母排除了谁？
□ 这个指标可加吗？跨维度 SUM 有意义吗？
□ 时间口径是自然日还是滚动窗口？
□ 有没有 WHERE 会让累计值倒退？
□ 和相邻指标（支付/退款/GMV）的差额来源说清了吗？
□ 改了之后，历史数据要不要重算？
```

| 症状 | 先查 |
| --- | --- |
| 累计曲线出现倒退 | 有 `WHERE` 过滤，改成"全量 + 单独列" |
| 两个报表差一点 | 粒度不同（行级 vs 订单级）或覆盖范围不同 |
| 各维度相加 ≠ 总体 | 指标不可加（去重计数/比率） |
| 比率算出来是 0 或 1 | 整数除法，`CAST` 或 `* 1.0` |
| 比率相加不等于 1 | 小数精度，判据放宽到 3 位 |
