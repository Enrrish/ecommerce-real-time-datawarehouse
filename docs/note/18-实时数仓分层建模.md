# 18 · 实时数仓分层建模

> 一句话：分层不是为了"看起来专业"，是为了让**同一份口径只实现一次**，
> 并且让"数据错了"这件事可以被逐层定位。少一层，排查成本翻倍。

---

## 一、通用知识

### 1.1 四层的职责

| 层 | 职责 | 允许做什么 | 禁止做什么 |
| --- | --- | --- | --- |
| **ODS** | 贴源 | 原样落库、加元信息列 | 过滤、聚合、改字段语义 |
| **DWD** | 明细 | 清洗、去重、打宽、统一口径 | 聚合到指标级 |
| **DWS** | 汇总 | 按主题/粒度聚合 | 跨主题混算 |
| **ADS** | 应用 | 面向具体报表/接口的宽表 | 被下游再加工 |

一句口诀：**ODS 只搬、DWD 只洗、DWS 只聚、ADS 只出**。

### 1.2 为什么必须分

**① 口径只实现一次**

"GMV 怎么算"如果写在 ADS 里，那么第二个报表要 GMV 时就会复制一份，
两处日后必然漂移。放在 DWD（明细层就有 `item_total`），所有下游都从同一个源头取。

**② 错误可定位**

```
ADS 的数字不对
  → 查 ADS 的聚合 SQL（范围最小）
  → 再查 DWS 的分组对不对
  → 再查 DWD 的行数和清洗规则
  → 最后查 ODS 与源的 diff
```

每层都有"与上游 diff 全 0"的验收，错误就被夹在某一层里。

**③ 变更影响可控**

源表加字段：只改 ODS + DWD。指标口径变：只改 DWS + ADS。

### 1.3 粒度设计：先定"一行是什么"

这是建模里最重要的一个决定，比字段名重要得多。

```
dwd_trade_order_detail   一行 = 一个订单行（order_id + order_item_id）
dws_trade_overview_1m    一行 = 一分钟
dws_trade_seller_1d      一行 = 一个卖家一天
dws_traffic_funnel_1h    一行 = 一小时的一个漏斗步骤
```

粒度错了，后面所有指标都会以"微妙的方式"错：比如把订单行当订单，
`COUNT(*)` 就会偏大（本项目 112,650 行 vs 98,666 单）。

### 1.4 流批边界

| | 流 | 批 |
| --- | --- | --- |
| 延迟 | 秒级 | 分钟~小时 |
| 状态 | 有（要 checkpoint） | 无 |
| 适合 | 明细同步、增量聚合 | 全量重算、复杂 join、维表加工 |

常见误区：**"实时数仓"不等于"所有层都用 Flink"**。

本项目里：

```
ODS / DWD / DWS  → Flink 流作业（增量、有状态）
ADS              → Doris 侧 INSERT OVERWRITE（批，全量重算）
维度表           → 一次性批处理（dim_date 生成、dim_geo 坐标聚合）
```

ADS 用批的理由：它是"面向大屏的最终形态"，需要"结果集即表的最终状态"
（包括删除）。流式 upsert 做不到"行消失"，批的 `INSERT OVERWRITE` 天然做到。

### 1.5 Lambda 与 Kappa

| | Lambda | Kappa |
| --- | --- | --- |
| 结构 | 批层 + 流层，两套代码 | 只有流层，重放历史 |
| 一致性 | 两套代码容易漂移 | 一套代码，天然一致 |
| 成本 | 两份计算 | 需要可重放的数据源（Kafka 保留期够长） |

本项目是**混合**：主体是流（Kappa 思路），但 ADS 与维表用批。
不是教条选择，而是"哪层适合哪种"。

### 1.6 命名规范

```
{层}_{主题}_{粒度}_{可选后缀}
ods_orders
dwd_trade_order_detail
dws_trade_overview_1m
ads_realtime_overview
dim_user_zip
```

好处：`SHOW TABLES` 按前缀就能分组，脚本里 `LIKE 'ods_%'` 能一次统计。

## 二、在本项目中

### 2.1 四层的实际规模

| 层 | 表数 | 行数（代表表） | 谁在写 |
| --- | --- | --- | --- |
| ODS | 10 | geolocation 1,000,163 | Flink CDC / Kafka source |
| DWD | 7 | `dwd_trade_order_detail` 112,650 | Flink（六表 join） |
| DWS | 6 | `dws_trade_overview_1m` 88,157 | Flink（聚合） |
| ADS | 7 | `ads_order_stream` 98,666 | Python 后端 `INSERT OVERWRITE` |

**每层都与上游做过 diff 全 0**（见 `21`）。

### 2.2 ODS：只加元信息列，不改语义

```sql
-- 列名、列序、语义与 MySQL 源表逐列一致（含源端拼写错误 lenght）
-- 末尾追加：op / ts_ms / dt
```

三个细节：

- **追加而不是插入**：Flink 的 `INSERT INTO ... SELECT` 按位置对齐，追加末尾列
  可以少一次人工对位
- **保留源端拼写错误**：`lenght` 不改。改了就和源表对不上，而且 diff 工具会误报
- **`ods_user_event` 没有 `op` 列**：Kafka 消息里没有"变更类型"这个概念

### 2.3 DWD：打宽与清洗

`dwd_trade_order_detail` 是六表 join：

```
order_items ⋈ orders ⋈ customers ⋈ products ⋈ sellers ⋈ category_translation
```

产出 112,650 行（订单行粒度），`SUM(item_total)` = 15,843,553.24。

为什么打宽到这一层：下游的类目/卖家/地域三个 DWS 表都要这些维度。
如果每个 DWS 自己 join，就是三份 join 状态（本项目实测这会直接 OOM，见 `10`）。

**打宽的成本是一次性的，不打宽的成本是每次查询都要付。**

### 2.4 DWS：按主题拆，不按层拆

| 表 | 粒度 | 主题 |
| --- | --- | --- |
| `dws_trade_overview_1m` | 分钟 | 全局概览 |
| `dws_trade_category_1d` | 天 × 类目 | 品类 |
| `dws_trade_seller_1d` | 天 × 卖家 | 卖家 |
| `dws_trade_region_1d` | 天 × 州 | 地域 |
| `dws_traffic_funnel_1h` | 小时 × 漏斗级 | 行为 |
| `dws_payment_method_1d` | 天 × 支付方式 | 支付 |

**一个作业只做一张表**。`STATEMENT SET` 想共享 join 的尝试失败了（投影不同 →
RelNode 不等 → 四份 join → 22 个 Join → OOM），拆开后单作业 50~90MB，安全。

### 2.5 ADS：面向大屏，不追求复用

```
ads_realtime_overview   顶栏 KPI + 趋势曲线
ads_category_rank_1d    品类排行
ads_funnel_1d           漏斗
ads_payment_method_1d   支付方式
ads_order_stream        右侧订单流水
ads_region_map_1d       地域气泡图
ads_pipeline_health     健康度
```

ADS 表的设计原则与前三层相反：**它服务于具体的面板**，字段名可以叫
`gmv`、`orders`，不必严格遵守维度建模。因为它不会被下游再加工。

### 2.6 一个刻意的"不做"

`docs/01` 里写过"ODS → DWD → DWS → ADS 的层间加工不在 Doris 内部做"，
但 P6 的 ADS 就是在 Doris 里用 `INSERT OVERWRITE` 做的。

这不是自相矛盾，而是**边界修正**：ADS 是"结果集即最终状态"，用 SQL 一次算完最简洁；
用 Flink 反而要为"行消失"这件事额外设计（见 1.4）。修正的理由写在了
`sql/doris/08-ads-refresh.sql` 的文件头。

**架构文档允许被现实修正，但修正必须留下理由** —— 否则下一个人会以为是遗漏。

### 2.7 踩过的坑

**坑 1：ODS 就做过滤，导致 diff 永远对不上**

最初想在 ODS 层就把 `order_status = 'canceled'` 剔掉。结果是"ODS 行数 ≠ 源表行数"，
diff 从此失去意义（无法区分"过滤掉了"和"丢数据了"）。

正解：ODS 全收，过滤放在 DWD 的 `WHERE` 或 ADS 的指标口径里。

**坑 2：DWS 用 AGGREGATE 模型承接流计算的"总值"**

流输出的是"这个分组的当前总值"，不是增量。AGGREGATE + SUM 会把总值当增量累加，
100 → 110 → 121。改用 UNIQUE（见 `15`）。

**坑 3：ADS 与 DWS 的粒度不对齐**

`ads_funnel_1d` 从 `dwd_user_event_clean` 回明细重算 UV，而不是从 `dws_traffic_funnel_1h`
上卷 —— 因为 UV 不可加（见 `20`）。**跨粒度上卷前先问：这个指标可加吗？**

## 三、速查

```
ODS  → 只搬 + 加元信息（op / ts_ms / dt）
DWD  → 清洗 + 去重 + 打宽（一行 = 最细业务粒度）
DWS  → 按主题聚合（一行 = 主题 × 时间粒度）
ADS  → 面向面板（字段可以为某个图表定制）
```

| 判断 | 放在哪一层 |
| --- | --- |
| 剔除脏数据 | DWD（不删，加 `is_valid` 标记更好） |
| 维表 join | DWD（打宽一次，下游复用） |
| 比率类指标 | ADS（分子分母都要能追溯） |
| UV / 去重计数 | 明细层（DWS 上卷会重复计数） |
| 全量重算 / 行消失 | ADS（`INSERT OVERWRITE`） |
