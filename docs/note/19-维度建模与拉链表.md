# 19 · 维度建模与拉链表

> 一句话：维度建模的核心不是"画星型图"，是**先把粒度说清，再决定哪些属性会变**。
> 会变的属性要么接受"只剩最新值"，要么用拉链把历史留下来 —— 这是一次业务选择。

---

## 一、通用知识

### 1.1 事实表与维表

| | 事实表 | 维表 |
| --- | --- | --- |
| 存什么 | **度量**（金额、数量） + 外键 | **描述**（名称、分类、地址） |
| 增长速度 | 快（随业务事件） | 慢（随主数据变更） |
| 行数 | 大 | 小 |
| 典型操作 | 聚合（SUM/COUNT） | join 补属性 |

事实表的一行 = 一个**业务事件在某个粒度上的记录**。
维表的一行 = 一个**实体的一个版本**。

### 1.2 星型与雪花

```
星型：事实表 ──┬── dim_date
              ├── dim_product
              ├── dim_user
              └── dim_geo

雪花：dim_product ── dim_category ── dim_category_group
```

| | 星型 | 雪花 |
| --- | --- | --- |
| 维表是否规范化 | 否（宽表，允许冗余） | 是（分层） |
| 查询 join 次数 | 少 | 多 |
| 更新成本 | 改一处要刷全宽表 | 改一处只影响一张 |

数仓普遍选星型：**查询性能优先，冗余可接受**。本项目 DWD 的宽表就是极端的星型
（把六个维度的属性全部拍进一张事实表）。

### 1.3 代理键与自然键

| | 自然键 | 代理键 |
| --- | --- | --- |
| 例子 | `order_id`、`customer_unique_id` | 自增 `id`、`hash(...)` |
| 优点 | 可追溯源系统 | 稳定、与源解耦、支持同实体多版本 |
| 缺点 | 源系统可能复用/变更 | 需要额外维护映射 |

拉链表的主键通常是 **`(自然键, 版本标识)`** —— 因为同一个实体有多个版本。

### 1.4 缓慢变化维（SCD）

| 类型 | 做法 | 保留历史 | 代价 |
| --- | --- | --- | --- |
| **SCD1** | 直接覆盖 | ❌ | 无（但历史报表会"变"） |
| **SCD2** | 加一行新版本，旧版本标记失效 | ✅ | 表变大，查询要带 `is_current` |
| SCD3 | 加一列"上一个值" | 只保留一版 | 只能回溯一层 |

SCD2 的标准结构：

```sql
CREATE TABLE dim_user_zip (
  user_id     VARCHAR(32) NOT NULL,
  start_date  DATETIME    NOT NULL,   -- 该版本生效时间
  end_date    DATETIME,               -- 失效时间；当前版本是 9999-12-31 23:59:59
  is_current  TINYINT,                -- 1 = 当前版本
  ...属性...
  UNIQUE KEY(user_id, start_date)
);
```

查询"某个时间点的状态"：

```sql
SELECT * FROM dim_user_zip
WHERE start_date <= '2026-11-01 00:00:00'
  AND end_date   >  '2026-11-01 00:00:00';
```

查询"当前状态"：

```sql
SELECT * FROM dim_user_zip WHERE is_current = 1;
```

### 1.5 要不要做拉链：一个业务判断

**不是所有维表都值得做 SCD2。** 判断标准：这个属性**会变吗**？变了**会影响历史报表吗**？

- 卖家城市会变，但历史订单的"卖家所在城市"应该按**下单时**算 → 需要 SCD2
- 商品类目会变，历史订单的类目归属应该按下单时 → 需要 SCD2
- 如果源系统根本不记录变更（只保留当前值），做 SCD2 只能得到"每行都是当前版本"的空壳

最后一种情况下，做 SCD2 是**自欺欺人**：表结构看起来专业，实际没有任何历史信息。

### 1.6 退化维与一致性维度

- **退化维**：把维度属性直接放在事实表里（如 `order_id` 本身就是维度，不需要单独建表）
- **一致性维度**：多个事实表共用同一套维表（如 `dim_date`），保证跨主题口径一致
- **角色扮演维**：同一张维表在事实表里出现多次（下单日期 / 支付日期 / 发货日期都指向 `dim_date`）

### 1.7 流里做维表 join 的三种方式

| 方式 | 实时性 | 状态成本 |
| --- | --- | --- |
| 预打宽（在 DWD 就 join 好） | 高 | 一次（但 join 状态大） |
| Lookup join（查外部维表） | 中（有缓存延迟） | 小 |
| 广播维表（`BROADCAST` hint） | 高 | 维表全量进每个并行子任务 |

本项目选"预打宽"，代价是 join 状态 134MB（见 `12`）。

## 二、在本项目中

### 2.1 五张维表

| 表 | 行数 | 建法 | 是否 SCD2 |
| --- | --- | --- | --- |
| `dim_date` | 4,383 | 生成（2010-01-01 ~ 2021-12-31） | 否（日期不变） |
| `dim_geo` | 19,015 | 由 `geolocation` 100 万行聚合 | 否 |
| `dim_seller` | 3,095 | CDC 全量 | **否**（源里没有变更历史） |
| `dim_user_zip` | 96,096 | CDC + 拉链结构 | **是**（结构上支持） |
| `dim_product_zip` | 32,951 | CDC + 拉链结构 | **是**（结构上支持） |

### 2.2 `dim_user_zip`：为什么不能用 `customer_id`

这是本项目最重要的一个建模判断：

```
99,441 个 customer_id  ↔  99,441 个订单     ← 一一对应，是"订单级主键"
96,096 个 customer_unique_id                ← 真正的人
```

差的那 **3,345** 就是复购人群。

按 `customer_id` 建拉链的后果：

```
每个客户只在下单那一刻出现一次，再无变更
→ 拉链退化成订单快照
→ 复购率、RFM、用户生命周期价值全部失效
```

所以 `dim_user_zip` 的粒度是 `customer_unique_id`。
**这是"粒度选错会让所有下游指标静默失效"的典型例子。**

### 2.3 `dim_seller` 为什么不做 SCD2

`sellers` 表只有 `seller_zip_code_prefix / seller_city / seller_state` 三个属性，
Olist 数据里**不存在变更历史**（每个卖家一行，永远不变）。

强行做拉链的结果：一张每行 `is_current=1` 的宽表，没有任何信息增量，
反而多一个 `start_date` 要维护。**不做**是正确选择，理由写在了建表注释里。

`dim_user_zip` 不同：它的 SCD2 结构是为了"以后真有变更时能留下历史"，
当前数据里每个用户也只有一版（`is_current=1`）。

### 2.4 `dim_geo`：100 万行怎么变成 1.9 万行

`geolocation` 是 `(zip_code_prefix, lat, lng, city, state)`，100 万行，
同一个邮编有几十个坐标点。

聚合方式：按邮编取**中心点**。两个必须处理的细节：

**① 11 个错坐标（0.06%）**

有些点的经纬度落在巴西境外（0,0 或写错的正负号）。直接平均会把中心点拉到海里。
做法：**先按巴西边界过滤，再聚合**。

**② 加权平均，不是简单平均**

同一个邮编下不同坐标点有重复次数（`point_cnt`）。简单平均会让"只出现一次的偏点"
和"出现一千次的主点"等权。做法：按 `point_cnt` 加权。

```sql
-- 伪代码
SUM(lat * point_cnt) / SUM(point_cnt)
```

`MEDIAN()` 也能用，但它**不接受 DECIMAL**，要先 `CAST` 成 DOUBLE。

### 2.5 宽表：六表 join 的取舍

`dwd_trade_order_detail` = `order_items ⋈ orders ⋈ customers ⋈ products ⋈ sellers ⋈ category_translation`

产出 112,650 行。为什么值得：

| 方案 | join 状态 | 下游成本 |
| --- | --- | --- |
| 不打宽，每个 DWS 自己 join | 每张 DWS 各一份（实测四份直接 OOM） | 每次查询都付 |
| 打宽一次 | 一份（134MB） | 一次 |

顺带解决了一个坑：`category_translation` 只有 71 行，而商品有 73 个类目 ——
**有 2 个类目翻不出来**。打宽时用 `LEFT JOIN` + `COALESCE(译名, 原名)`，
否则这 2 个类目的商品会被 join 丢掉。

### 2.6 退化维的用法

`ads_order_stream` 里直接放 `order_id`、`customer_city`，不建维表 ——
大屏只需要"最近 8 笔订单"的展示，不需要按城市做分析。这是**面向用途的简化**，
不是建模缺陷。

### 2.7 踩过的坑

**坑 1：用 `customer_id` 当用户粒度**

见 2.2。所有用户价值指标失效，且不报错。

**坑 2：`dim_geo` 直接 `AVG(lat)`**

11 个错坐标会把中心点拉偏。判据：聚合后中心点是否落在巴西范围内
（经度 -74 ~ -34，纬度 5 ~ -34）。

**坑 3：`LEFT JOIN` 写成 `JOIN`，丢 2 个类目**

`category_translation` 缺 2 个类目 → `JOIN` 会让这 2 个类目的商品消失。
行数从 112,650 变成 112,6xx，diff 才发现。

**坑 4：拉链表的 `end_date` 用 `NULL` 表示当前**

查询 `WHERE end_date > '...'` 时 `NULL` 比较永远为 false，当前版本查不出来。
用 `9999-12-31 23:59:59` 而不是 `NULL`。

## 三、速查

```sql
-- 当前版本
SELECT * FROM dim_user_zip WHERE is_current = 1;

-- 某个时间点的版本
SELECT * FROM dim_user_zip
WHERE start_date <= '2026-11-01' AND end_date > '2026-11-01';

-- 拉链表主键
UNIQUE KEY(`customer_unique_id`, `start_date`)
```

| 判断 | 结论 |
| --- | --- |
| 属性永不变（日期） | 不建拉链 |
| 属性会变，但源里没历史 | 不建拉链（建了也是空壳） |
| 属性会变，历史报表要按下单时算 | 建 SCD2 |
| 只需要最新值 | SCD1（直接覆盖） |
| 粒度选不准 | 先问"一行代表什么业务实体" |
