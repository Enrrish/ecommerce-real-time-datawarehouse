# 13 · 时间语义与 Watermark

> 一句话：在流里，"现在几点"是一个**判断题**，不是一个事实。Watermark 就是你对这个
> 判断题的答案："我认为早于 T 的事件不会再来了"。答得太乐观会丢数据，太保守会卡住。

---

## 一、通用知识

### 1.1 三种时间

| 时间 | 含义 | 谁决定 | 用途 |
| --- | --- | --- | --- |
| **事件时间** `event_time` | 事件真实发生的时间 | 产生方（埋点、业务库） | 窗口、乱序处理、可重放 |
| **摄入时间** `ingest_time` | 进入 Flink source 的时间 | source | 少用 |
| **处理时间** `proc_time` | 算子处理它时的机器时间 | 算子 | 去重、lookup、限流 |

只有事件时间能保证**重算结果一致**（同一批数据跑两遍结果相同）。处理时间不能 ——
它依赖"什么时候跑的"。

### 1.2 Watermark 是什么

```
W(t) = 一个单调递增的时间戳，含义是"event_time <= W 的数据已经到齐了"
```

窗口的触发条件：`watermark >= window_end`。所以：

- **watermark 推进得快** → 窗口早触发，迟到数据被丢
- **watermark 推进得慢** → 结果准，但延迟大、状态积压

生成方式：

```sql
-- 有界乱序：允许迟到 5 秒
WATERMARK FOR event_time AS event_time - INTERVAL '5' SECOND

-- 严格单调（不允许乱序，一般不用于真实数据）
WATERMARK FOR event_time AS event_time
```

### 1.3 迟到数据会怎样

默认：**丢弃**（不报错，不计数）。

三个补救手段：

| 手段 | 效果 |
| --- | --- |
| `allowed lateness` | 窗口关闭后再等一会儿，迟到数据还能更新结果 |
| side output（`getSideOutput`） | 把迟到数据分流到另一个流，单独处理 |
| 不用窗口 | 用 `GROUP BY` 更新流 + `PROCTIME()` 去重（本项目的选择） |

### 1.4 三个"水位线不动"的经典原因

**① 某个分区没数据（idle）**

多分区 source 里，watermark 取所有分区的**最小值**。一个分区长期没数据，
它的 watermark 停在原地，整条流的水位线就不动 —— 窗口永远不触发。

修法：`table.exec.source.idle-timeout: 30s`（分区空闲超过阈值就暂时忽略它）。

**② 上游数据的事件时间在未来**

一条 `event_time = 明天` 的记录会把 watermark 直接推到明天，
之后所有正常数据都成了"迟到"，被全部丢弃。

现象：**生产了几万条，下游只统计到一小部分**。而且不报错。

**③ 用了 `latest-offset` 之类的"半截数据"**

没有历史数据把水位线"垫起来"，第一批数据的事件时间跨度又大，水位线跳变。

### 1.5 处理时间不要去猜"顺序"

`PROCTIME()` 单调递增但**不保证与事件顺序一致**（并行、网络抖动）。
它适合"取一条"（去重），不适合"按业务顺序取最后一条"。

### 1.6 时区

- `TIMESTAMP` 无时区；`TIMESTAMP_LTZ` 带时区（内部 epoch）
- `table.local-time-zone` 影响 `CURRENT_TIMESTAMP` / `PROCTIME()` 的显示
- **写入型时间函数**（`NOW()`、`CURRENT_TIMESTAMP`）在流里是"处理时间"语义，
  每条形参一次，不能用来做业务时间

## 二、在本项目中

### 2.1 只有一条链有"时间"问题

| 链路 | 有没有事件时间 | 为什么 |
| --- | --- | --- |
| MySQL CDC → ODS | 有（业务时间字段），但**不做窗口** | 只是搬运 + 打宽 |
| Kafka 埋点 → ODS/DWD | 有（`event_time`） | 漏斗按天/小时聚合，但用的是 `GROUP BY` 而非窗口 |
| 07 分钟概览 | 有（`order_purchase_timestamp`） | 同上，`GROUP BY` 更新流 |

也就是说：**本项目刻意不用窗口**。理由写在 `07` 的文件头：

```
不用窗口，这是刻意的。
分钟概览需要"每个 dt+minute 一行，值随新数据更新"，这是更新流语义，
不是"窗口结束时输出一次"。
```

不用窗口就没有"水位线卡住"的问题，代价是状态量等于分组数（8.8 万），比窗口大。

### 2.2 但 `PROCTIME()` 还是用了

`09` 从 Kafka 直连算漏斗，要按 `event_id` 去重：

```sql
ROW_NUMBER() OVER (PARTITION BY event_id ORDER BY PROCTIME()) = 1
```

为什么不用 `event_time` 排序：流模式下 OVER 聚合强制 `ORDER BY` 落在时间属性上，
用事件时间会绑定 watermark；而上游 `earliest-offset` 重放时水位线永远落后，
**尾部记录卡在状态里不出**。

实测：22,064 条只落了 21,996 条 —— 差的 68 条就卡在那儿。

### 2.3 埋点生成器的第三条设计原则

`scripts/gen_user_events.py` 的注释里写着：

```
3. event_time 严格不晚于当前时刻。会话起点在窗口内随机，后续动作按偏移累加；
   若起点太晚导致末尾越界，就把整个会话往前挪。
   否则 Flink 的 watermark 会把这些"未来数据"判为迟到并丢弃，
   现象是「生产了几万条，漏斗只统计到一半」，极难排查。
```

这条不是理论 —— 它是 1.4 的第 ② 种情况。会话是"曝光 → 加购 → 提交 → 支付"，
每一步有几分钟的自然延迟。如果起点取 `now()`，支付那一步的 `event_time` 就在未来。

修法不是"调 watermark"，而是**生成时保证不越界**：起点在 `[now - 时长, now - 时长]` 内取，
越界就整体前移。**数据源的问题要在数据源修**。

### 2.4 `late_ratio`：怎么定义"迟到"

健康度里的 `late_ratio` 不是 Flink 的指标，是自己算的：

```
近 10 分钟内抽样的 N 条里，event_time 比「本分区已见最大 event_time」落后 > 60s 的比例
```

三个口径细节，每一个都踩过：

**① 必须按分区分别算**

跨分区比较没意义 —— Kafka 只保证分区内有序。所以抽样时要跨分区均分，
"本分区的最大值"才是正确的参照。

**② 必须只看最近 N 条（滑动窗口），不能用全量累计**

全量累计会被历史稀释：实际 2.91%，全量算出来 0.19%。

**③ 还必须再按时间切一刀（`HORIZON = 10 分钟`）**

采样窗口里混入"批量回填"时，回填事件的 `event_time` 是 1 小时前的。
一旦前面有新鲜事件把分区最大值抬到"现在"，整批回填全被算成乱序：

```
注入 5% → 报 66.67%
```

现在规则是：`> 10 分钟` 的只计数、不参与判定（"回填"这件事交给 `event_age_p99_s`）。

**正向对照**：`scripts/calibrate_late_ratio.py` 发 2117 条近期事件、其中 290 条故意迟到，
指标报 **13.6986%**（= 290/2117），分子分母都对。

> 只验证"过滤后变 0"不算数 —— 那可能只是把信号一起滤掉了。

### 2.5 `event_age_p99_s`：另一个时间指标

```
含义：最近 600 秒内写入的事件，其 event_time 距离现在多久（P99）
正常：5 秒左右
```

这个指标会**必现地亮红约 10 分钟**：每次重投 04/06/09（`earliest-offset`）都会重放
整个 topic（14.9 万条 / 6.5 分钟），把 5 天前的事件用"现在"的 `ts_ms` 重写一遍。
而指标窗口正是 `ts_ms >= now - 600s` —— **重放本身就在窗口里**。

实测：重放 `16:23:55 → 16:26:40`，指标在 **`16:36:40`**（结束 + 600 秒）准时回到 5 秒。

```sql
-- 判据：这个数掉回正常量级，指标自然恢复
SELECT COUNT(*) FROM ods_user_event WHERE ts_ms >= (UNIX_TIMESTAMP() - 600) * 1000;
```

**不要改阈值，不要加 `event_time > now() - interval 1 hour` 过滤** ——
那会把真正的积压一起滤掉。

### 2.6 时间精度的两个事实

| 事实 | 后果 |
| --- | --- |
| binlog 事件头时间戳只有**秒** | 由 `op_ts` 派生的 `ts_ms` 后三位恒 `000` |
| 埋点 `event_time` 是毫秒字符串 | 解析要 `TIMESTAMP(3)`，格式 `yyyy-MM-dd HH:mm:ss.SSS` |

## 三、速查

```sql
-- 事件时间 + 有界乱序
event_time TIMESTAMP(3),
WATERMARK FOR event_time AS event_time - INTERVAL '5' SECOND

-- 处理时间（去重首选）
proc_time AS PROCTIME()

-- 允许迟到（窗口场景）
-- 窗口 TVF + allowed lateness 需配合 windowing TVF 参数
```

| 现象 | 原因 |
| --- | --- |
| 生产几万条，下游只收到一部分 | 有 `event_time` 在未来的记录，watermark 被推到未来 |
| 窗口永不触发 | 某个分区 idle（`table.exec.source.idle-timeout`） |
| 尾部几十条卡住不出 | `ROW_NUMBER` 用了事件时间，水位线不推进 |
| `late_ratio` 高得离谱 | 采样窗口混入批量回填，要加 HORIZON |
| `event_age_p99_s` 亮红约 10 分钟 | 刚重放过 topic，正常 |
| `ts_ms` 末三位总是 000 | binlog 事件头是秒精度 |
