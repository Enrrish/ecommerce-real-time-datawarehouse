# 21 · 数据质量与一致性校验

> 一句话：数据质量不是"跑几个断言"，而是**让"数据错了"这件事在没人盯着的时候也能被发现**。
> 而最难的部分不是发现错误，是**不把"没测到"当成"没问题"**。

---

## 一、通用知识

### 1.1 六个质量维度

| 维度 | 问什么 | 典型指标 |
| --- | --- | --- |
| 完整性 | 该来的都来了吗 | 行数、非空率 |
| 唯一性 | 有没有重复 | 主键重复率 |
| 及时性 | 来得多快 | 延迟、积压 |
| 有效性 | 格式对吗 | 枚举外值、负金额 |
| 一致性 | 各层对得上吗 | 逐表 diff |
| 准确性 | 值对吗 | 与源系统对账 |

### 1.2 一致性校验：diff 是核心手段

```
源表 COUNT(*)  ==  ODS COUNT(*)          （全量同步后）
ODS 去重后 COUNT(*)  ==  DWD COUNT(*)     （清洗后）
DWD SUM(item_total)  ==  DWS SUM(gmv)     （聚合后）
DWS 行数  >=  ADS 行数                     （收敛后）
```

**diff 必须是"逐表、逐指标"的**，不能只看总数 —— 两张表都少 10 行，总数对得上，
但内容已经错了。

### 1.3 幂等重放测试

```
① 记录当前行数 N
② 取消作业，重新提交（重放全部数据）
③ 再查行数，仍为 N → 幂等
   变成 2N → 不幂等
```

这是最能证明"模型选对了"的测试。DUPLICATE 模型必然变 2N，UNIQUE 模型恒定。

### 1.4 脏数据注入

主动造脏数据，看链路是"拒绝"还是"吞掉"：

| 注入 | 期望 |
| --- | --- |
| 3% 重复（同 `event_id`） | 行数不变（幂等） |
| 5% 乱序（迟到 5 分钟） | 指标能报出这个比例 |
| 空 JSON `{}` | 作业不挂（可观测的降级） |
| 超长字段 | 明确报错，不是静默截断 |

关键：**注入的量要可计算**。注入 5% 就要能算出期望值，否则"看起来差不多"不算验证。

### 1.5 正向对照（positive control）

这是最容易被跳过、也最重要的一步：

```
只验证"过滤后变 0"     → 可能把信号和噪声一起滤掉了
验证"注入已知比例 → 指标等于该比例" → 才证明分子分母都对
```

类比：检测仪归零不能证明它能测出东西，得拿标准样品测一次。

### 1.6 "没测到"不能报成"测到 0"

这是数据质量里最隐蔽的一类错误：

```python
latency = measure() or 0        # 测量失败 → 0ms → "完美"
```

```bash
[[ "$api" != "$baseline" ]]     # 接口 500 返回 "ERR" → 不等于基线 → "命中"
```

```bash
[[ "$n" -lt 5 ]] && echo "0%"   # 分母为 0 → 0% → "零乱序，很健康"
```

三种写法都会把"故障"变成"好成绩"。正确做法：

- 测量失败 → 标记为"未测到"，**不参与判定**，并单独暴露"未测到"这个状态
- 分母为 0 → 不写这一行指标（而不是写 0）
- 校验失败 → 失败，不是"不相等就算过"

### 1.7 告警分级

```
ok      正常
warn    需要关注，但业务可继续
critical 必须处理
```

分级的意义是**让人能区分"现在就修"和"记一下"**。全是 critical 等于没有告警。

### 1.8 抽样的三个陷阱

| 陷阱 | 后果 |
| --- | --- |
| 全量累计而非滑动窗口 | 历史稀释，2.91% 测成 0.19% |
| 只抽一个分区 | 跨分区无序被误判为有序 |
| 窗口混入批量回填 | 回填全被算成乱序，5% 报成 66.67% |

## 二、在本项目中

### 2.1 逐表 diff：每一层都做过

| 层 | 表数 | 方法 | 结果 |
| --- | --- | --- | --- |
| ODS | 10 | 与 MySQL 逐表 `COUNT(*)` + 关键列 `SUM` | 全 0 |
| DWD | 7 | 与 ODS 去重后的结果比 | 全 0 |
| DWS | 6 | 与 DWD 重算的结果比 | 全 0 |
| ADS | 7 | 与 DWS 上卷的结果比 | 全 0 |

"全 0"的意思不是"差 0 行"，是**每一张表的行数与关键指标差值都为 0**。

### 2.2 幂等重放

`04/06/09` 三个 Kafka 源都是 `earliest-offset`，每次重投都重放整个 topic。
这本来是"为了拿到历史数据"的无奈选择，顺手变成了**天然的幂等测试**：

```
重放前 dwd_user_event_clean  22,004 行
重放后（14.9 万条全部重放）   22,004 行
```

如果 `UNIQUE(event_id, dt)` 没生效，这里会变成 4 万+。

### 2.3 脏数据注入：3,091 条

```
--dup-rate 0.03 --late-rate 0.05，注入 3,000 条重复 + 乱序
实际进入 ODS 3,091 条（含 91 条格式异常）
DWD 清洗后 +3,001 条（90 条被 is_valid 标记但保留，1 条彻底丢弃）
DWS/ADS 只 +3,001
```

关键观察：**脏数据没有被"静默吞掉"**，而是被 `is_valid` / `invalid_reason` 记录下来。
这让"脏了多少"变成可查的数字，而不是"感觉差不多"。

### 2.4 `late_ratio` 的正向对照

```
注入：2,117 条近期事件，其中 290 条故意迟到 ≥ 5 分钟
期望：290 / 2117 = 13.6986%
实测：13.6986%      ← 分子分母都对
```

为什么必须做这一步：在此之前，`late_ratio` 曾把 5% 的注入报成 **66.67%**。
如果只验证"过滤后变 0"，会误以为修好了 —— 实际是把信号一起滤掉了。

修法的三层：

1. 只看最近 N 条（滑动窗口），不用全量
2. 跨分区均分抽样，按"本分区最大值"判迟到
3. 再加 `HORIZON = 10 分钟`：超过 10 分钟的只计数，不参与判定（回填交给 `event_age_p99_s`）

### 2.5 十一个健康度指标

写进 `ads_pipeline_health`，大屏底部展示：

| 组 | 指标 | ok 判据 |
| --- | --- | --- |
| delay | `e2e_latency_ms` | < 5000 |
| delay | `pipeline_freshness_s` | < 300 |
| delay | `event_age_p99_s` | < 60 |
| quality | `dup_rate` | < 1% |
| quality | `late_ratio` | < 5% |
| quality | `canceled_gmv` / `canceled_ratio` | < 1% |
| capacity | `checkpoint_p95_ms` | < 5000 |
| capacity | `flink_jobs_running` | 3~4 |
| capacity | `kafka_lag` | < 1000 |
| capacity | **`overview_join_rows`** | **≥ 40 万** |

最后一项是后来加的，因为前面十项**一起漏掉了一个僵尸作业**（原理见 [11](11-Flink-CDC.md)，
项目侧完整复盘见 [docs/07-事故库](../07-事故库.md) 的 `A1`）：
作业 `RUNNING`、checkpoint 正常、lag 0、十项全 ok，但一行不写。

`overview_join_rows` 是 07 四个源累计读取行数，是"join 状态已填满"的直接证据。

### 2.6 "没测到"报成 0：本项目踩过四次

| # | 位置 | 错误写法 | 后果 |
| --- | --- | --- | --- |
| 1 | `e2e_latency_ms` | 测不到 → 返回常量 3849 | 面板显示"3.8 秒"，实际没测 |
| 2 | `late_ratio` | 分母 0 → 写 0% | "零乱序，很健康" |
| 3 | `--skip-kafka` | 不采集却保留上次值 | 看不出是旧数据 |
| 4 | 今日空态 | 没数据 → 显示 `¥0.00` | 看起来"今天没成交" |

修法四条（已落地）：

- 测不到就**不写这一行**，并在页面上显示"暂无"
- 分母为 0 不写指标
- `--skip-kafka` 时明确打印"保留上次采集值"
- 今日无数据时显示 `暂无 [CDC]` 而不是 `0`

### 2.7 关停快照：把"有没有丢数据"变成可比较的数字

`scripts/stop.sh` 在停容器**之前**把 7 张表的行数写进 `.shutdown-snapshot.txt`，
下次 `--status` 逐表对比。

判据要写清方向：

```
核心表（DWD/DWS/ADS）  行数必须完全一致
埋点表（ods/dwd_user_event）  上升正常（停机期 Kafka 积压补消费），下降才是丢数据
```

没有这条基线，"数据没丢"只能靠感觉。

### 2.8 一个反例：验收脚本的失败会伪装成成功

早期版本：

```bash
API_GMV() { curl -s ... || echo "ERR"; }
[[ "$api" != "$b_api" ]] && echo "可见 306ms"
```

接口 500 时返回 `ERR`，`ERR != "110.00"` 成立 → 立刻记成"命中"，
而且脚本 `exit 0`。**接口全程 500 也能打印出一份漂亮的验收报告。**

修法：

```bash
curl -f                            # 非 2xx 直接失败
[[ "$api" =~ ^[0-9]+\.[0-9]{2}$ ]]  # 输出格式校验
失败不参与命中                      # 不计入 min/max
连续 3 次失败 → FAIL + exit 1
```

这条的通用形式：**验收脚本本身也要被验收。**

## 三、速查

```sql
-- 逐表行数对账
SELECT 'dwd' src, COUNT(*) FROM realtime_dw.dwd_trade_order_detail
UNION ALL SELECT 'dws', COUNT(*) FROM realtime_dw.dws_trade_overview_1m;

-- 关键指标对账
SELECT SUM(item_total) FROM realtime_dw.dwd_trade_order_detail;   -- 15,843,553.24
SELECT SUM(gmv)        FROM realtime_dw.dws_trade_overview_1m;    -- 应一致

-- 重复率（滑动窗口，不要全量）
SELECT 1 - COUNT(DISTINCT event_id) / COUNT(*) FROM (
  SELECT event_id FROM realtime_dw.ods_user_event ORDER BY ts_ms DESC LIMIT 1000
);
```

```bash
# 幂等重放
before=$(count dwd_user_event_clean)
bash scripts/demo.sh --no-dashboard      # 重投作业
after=$(count dwd_user_event_clean)
[[ "$before" = "$after" ]] && echo "幂等 ✓"

# 正向对照
python scripts/calibrate_late_ratio.py --dry-run
python scripts/calibrate_late_ratio.py
```

| 症状 | 先查 |
| --- | --- |
| 行数比预期少 | 有 `JOIN` 而不是 `LEFT JOIN` / 有 `WHERE` 过滤 |
| 行数比预期多 | 不幂等（DUPLICATE 模型 / 重复消费） |
| 指标"完美"得可疑 | 是不是"没测到报成 0" |
| 注入比例对不上 | 抽样窗口混入了回填 / 分母取错 |
| 验收全绿但用户说不对 | 验收脚本自己的失败处理 |
