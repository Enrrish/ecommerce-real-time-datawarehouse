# 25 · 可观测性与链路健康度

> 一句话：可观测性不是"多埋几个指标"，是**在你不在场的时候，系统能告诉你它坏了**。
> 最难的不是采集，是设计出"坏了就一定会变红"的指标。

---

## 一、通用知识

### 1.1 三大支柱

| | 指标 metrics | 日志 logs | 链路 traces |
| --- | --- | --- | --- |
| 形态 | 数值 + 时间戳 | 文本 | 请求 ID + 跨度 |
| 擅长 | 趋势、告警 | 定位具体原因 | 定位慢在哪一跳 |
| 成本 | 低 | 中（体积） | 高 |

本项目的组合：**指标（11 项）+ 各组件日志（按需查）+ 无 trace**。
理由：单机 4 个作业，链路只有一条主路径，trace 的收益不抵成本。

### 1.2 黄金四信号

| 信号 | 问什么 | 本项目的对应 |
| --- | --- | --- |
| 延迟 Latency | 多快 | `e2e_latency_ms` / `event_age_p99_s` |
| 流量 Traffic | 多少 | `overview_join_rows` / `kafka_lag` |
| 错误 Errors | 错多少 | `dup_rate` / `late_ratio` |
| 饱和度 Saturation | 多满 | `checkpoint_p95_ms` / `canceled_ratio` |

### 1.3 判活 ≠ 判性能 ≠ 判质量

这是三个不同的问题，指标不能混用：

| 问题 | 例子 | 需要的指标 |
| --- | --- | --- |
| **活着吗** | 作业还在跑吗？数据还在流动吗？ | 行数、位点、心跳 |
| **性能好吗** | 延迟多少？checkpoint 多久？ | P95、吞吐 |
| **数据对吗** | 重复率？迟到率？ | 质量指标 |

**最容易犯的错：用"性能指标"回答"活着吗"。**

```
counter = 0  → 是"没有新数据"还是"计数器没更新"？
latency = 0  → 是"很快"还是"没测到"？
```

### 1.4 口径比数值重要

同一个东西，MIN / MAX / AVG 差别巨大：

```
pipeline_freshness_s：
  取 MAX（最旧的那张表）  → 任一条链停了就变红  ✅
  取 MIN（最新的那张表）  → 只要有一条链在写就是 0  ❌ 永远绿
```

本项目踩过这个坑：`pipeline_freshness_s` 取的是三张表 `update_time` 的最近者，
而 ADS 每 60 秒批刷会刷新 `update_time` —— **交易链停多久都显示 0 秒**。

### 1.5 阈值设计

| 方式 | 优点 | 缺点 |
| --- | --- | --- |
| 固定绝对值（<1000） | 简单 | 业务量变了就失效 |
| 相对变化（比昨天高 2 倍） | 自适应 | 需要历史基线，冷启动难 |
| 分级（ok/warn/critical） | 能区分"现在修"和"记一下" | 阈值要调 |

**全是 critical 等于没有告警。** 分级的意义是让人能排优先级。

### 1.6 反模式清单

| 反模式 | 后果 |
| --- | --- |
| 用缓存值判活 | Flink UI 的 `read-records` 长期 0，误判"作业空转" |
| 用聚合值掩盖明细 | 平均值正常，但某个分区全挂 |
| "没测到"记成 0 | 故障被记成"完美"（见 [21](21-数据质量与一致性校验.md)） |
| 指标没有时间戳 | 无法判断是"现在"还是"上次的" |
| 阈值与业务量绑定 | 数据涨 10 倍后全变红 |

### 1.7 指标要能落到表里，才能被查

```
写进数据库  → 能画趋势、能对比历史、能被 SQL 查
只打日志    → 只能人肉 grep
只在内存里  → 重启即丢
```

本项目把 11 项写进 Doris 的 `ads_pipeline_health`，大屏直接读。

## 二、在本项目中

### 2.1 指标表结构

```sql
CREATE TABLE ads_pipeline_health (
  metric_key      VARCHAR(64),    -- e2e_latency_ms
  metric_name     VARCHAR(64),    -- 端到端延迟
  metric_value    DOUBLE,
  metric_unit     VARCHAR(16),    -- ms / s / % / 条 / 元 / 个 / 行
  metric_level    VARCHAR(16),    -- ok / warn / critical
  threshold_desc  VARCHAR(255),   -- 判据说明（按字节算，中文 3 字节/字！）
  metric_group    VARCHAR(16),    -- delay / quality / capacity
  collect_time    DATETIME
);
```

`threshold_desc` 的 255 是**字节**，中文只能写 85 字。写长了整条 INSERT 被 strict mode
拒掉，报 `Insert has filtered data in strict mode` 且不带列名。

### 2.2 十一项指标

| 组 | key | 含义 | ok | warn |
| --- | --- | --- | --- | --- |
| delay | `e2e_latency_ms` | 端到端延迟 | < 5000 | < 15000 |
| delay | `pipeline_freshness_s` | 管道新鲜度（**MIN 口径**） | < 300 | < 3600 |
| delay | `event_age_p99_s` | 事件年龄 P99 | < 60 | < 300 |
| quality | `dup_rate` | 事件重复率 | < 1% | < 5% |
| quality | `late_ratio` | 事件乱序比例 | < 5% | < 20% |
| quality | `canceled_gmv` | 无效交易金额 | 参考 | — |
| quality | `canceled_ratio` | 无效交易占比 | < 1% | < 3% |
| capacity | `checkpoint_p95_ms` | Checkpoint P95 | < 5000 | < 15000 |
| capacity | `flink_jobs_running` | 运行中作业数 | 3~4 | — |
| capacity | `kafka_lag` | Kafka 积压 | < 1000 | < 10000 |
| capacity | **`overview_join_rows`** | 交易链 join 行数 | **≥ 40 万** | — |

### 2.3 第十一项是怎么补上的

前九项（原先十项）**一起漏掉了一个僵尸作业**：

```
07 作业：RUNNING、checkpoint 正常、lag 0、健康度 10 项全 ok
但一行不写，持续 47 分钟
```

为什么十项都没发现：

| 指标 | 为什么没报 |
| --- | --- |
| `flink_jobs_running` | 作业确实 RUNNING |
| `checkpoint_p95_ms` | checkpoint 确实正常（没有状态变化） |
| `kafka_lag` | 本作业不读 Kafka |
| `pipeline_freshness_s` | **MIN 口径**：ADS 每 60s 批刷会刷新 `update_time` |
| `e2e_latency_ms` | 测的是"改一行 MySQL → ADS"，这条链走的是别的作业 |

补上的 `overview_join_rows` 直接读 07 四个源的累计读取行数（Flink REST 的
`numRecordsOut`），**是"join 状态已填满"的直接证据**，判据 ≥ 40 万。

这条的通用形式：**每个"可能停摆"的组件都要有一个"它真的在动"的证据，
不能只看"进程活着"。**

### 2.4 采集脚本的失败处理

`collect-pipeline-health.sh` 的原则：

```bash
# ① 采集不到就不写这一行，而不是写 0
if [[ -n "$OVERVIEW_JOIN" ]]; then
  EXTRA_ROW=", ('overview_join_rows', ...)"
fi

# ② 分母为 0 不写
if [[ "$LATE_MEASURED" -eq 1 ]]; then
  LATE_ROW=", ('late_ratio', ...)"
fi

# ③ 跳过采集要明说
echo "    --skip-kafka：dup_rate / late_ratio / kafka_lag 保留上次采集值"
```

第三条尤其重要：`--skip-kafka` 时不写这三项，但也不能假装"刚采过"。
大屏上看到的值可能是上一次的 —— 所以脚本必须把这件事说出来。

### 2.5 时间口径：`e2e_latency_ms` 怎么测

```
改一行 MySQL → 记 t0
轮询 ADS 直到 GMV 变了 → 记 t1
e2e = t1 - t0
```

两个细节：

- 轮询间隔决定了测量精度（本项目 200ms）
- 测量失败（接口 500）**不能记成"很快"** —— 曾经的写法是 `|| echo "ERR"`，
  `ERR != 基线` 立刻被记成"命中"，接口全程 500 也能打印出"可见 306ms"

### 2.6 采集脚本的另一个坑：`checkpoint_p95_ms` 的口径

```
summary  → 全生命周期，被初始快照期的慢 checkpoint 拖住，长期误报
history  → 最近 10 次，反映"现在"
```

改成 history 后，P95 从"几十秒"恢复到"几百毫秒" —— 不是系统变快了，
是**指标终于测的是现在**。

### 2.7 大屏底部的健康度面板

11 项按三组展示，颜色对应 `metric_level`。它同时是**演示时的自证**：

```
面试官：你怎么知道链路是好的？
你：这 11 项，其中第 11 项是唯一能发现"作业 RUNNING 但一行不写"的指标。
```

这比"我看日志没报错"有说服力得多。

## 三、速查

```bash
# 采一次全量
bash scripts/collect-pipeline-health.sh

# 只看某一项
bash scripts/collect-pipeline-health.sh 2>&1 | grep overview_join_rows

# 跳过 Kafka 抽样（快）
bash scripts/collect-pipeline-health.sh --skip-kafka
```

```sql
-- 最近一次采集
SELECT metric_group, metric_key, metric_name, metric_value, metric_unit, metric_level
FROM ads_pipeline_health ORDER BY metric_group, metric_key;

-- 某项的趋势
SELECT collect_time, metric_value FROM ads_pipeline_health
WHERE metric_key = 'e2e_latency_ms' ORDER BY collect_time DESC LIMIT 20;
```

| 想判断 | 看哪个 |
| --- | --- |
| 作业活着吗 | `flink_jobs_running` + **目标表行数** |
| 数据在流动吗 | `overview_join_rows`（交易链）/ `event_age_p99_s`（行为链） |
| 延迟正常吗 | `e2e_latency_ms` + `checkpoint_p95_ms` |
| 数据干净吗 | `dup_rate` + `late_ratio` |
| 消费跟得上吗 | `kafka_lag` |
