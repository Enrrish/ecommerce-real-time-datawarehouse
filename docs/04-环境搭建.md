# 环境搭建

> 本文档是全项目**唯一的版本来源**。任何版本号改动必须同时更新这里、`docker/docker-compose.yml` 的镜像 tag、以及 `flink/lib/` 下的 jar 清单，三者不一致会直接导致运行期 `NoSuchMethodError`。

## 2. 兼容性链路：为什么是这一组

版本不是各挑最新，而是**从 Flink 反推**，因为 Flink 是唯一一个要和另外三个组件同时握手的节点。

```
MySQL 8.0.36 ──(flink-sql-connector-mysql-cdc-3.2.1)──┐
                                                      ├──► Flink 1.18.1 ──(flink-doris-connector-1.18-24.0.1)──► Doris 2.1.11
Kafka 3.7.1  ──(flink-sql-connector-kafka-3.1.0-1.18)─┘
```

四条约束逐跳对上：

1. **Flink CDC 3.2.x → Flink 1.17 / 1.18 / 1.19**
   官方兼容表：3.0.x 支持 1.14–1.18，3.1.x 支持 1.16–1.19（仅 3.1.1 支持 1.19），3.2.x 支持 1.17–1.19，3.3.x 起要求 1.19+。
2. **Doris Flink Connector → 制品名带 Flink 次版本号**
   `flink-doris-connector-<flink-minor>-<connector-version>.jar`。1.6.1 覆盖 Flink 1.15–1.19，24.0.1 覆盖 1.15–1.20。Flink 1.18 有独立制品，用错了不会报编译错，而是运行期类型不匹配。
3. **Flink Kafka Connector → 3.1.0 对应 Flink 1.18**
   SQL 版 jar 的命名规则同样是 `<connector>-<flink>`，`3.1.0-1.18` 即为此意。
4. **JDK 必须 11，不能 17**
   Flink 1.18 的 `flink-scala_2.12-1.18.1.jar` 用旧版 Scala 编译器构建，在 Java 17 镜像下走 Scala API 会直接抛 `ReflectiveOperationException`（FLINK-34658）。虽然本项目主体是 FlinkSQL、不直接写 Scala，但 Table API 内部仍会加载该包，没有必要冒这个险。

> 这条链子最脆弱的一环是 **Doris Connector 的制品名**，它是唯一一个把 Flink 次版本号写进文件名里的。升级 Flink 时如果忘了换这个 jar，集群能起来、作业能提交，但第一条数据写 Doris 时才炸。

## 3. 为什么不选更新的版本

面试官大概率会问「为什么不用 Flink 1.20」，答案必须能张口就来：

| 候选 | 否决理由 |
| --- | --- |
| Flink 1.20 | CDC 必须同步升到 3.3.x，Doris Connector 必须升到 26.x，三个组件一起跳；一旦出问题无法定位是哪个组件引入的。调试成本远高于收益，本地也不需要 1.20 的新特性 |
| Doris 3.x | 存算分离架构改动大，单机 Docker 部署的公开资料少，BE 默认内存基线也更高 |
| MySQL 8.4 | 不在 Flink CDC 的官方支持列表（5.6 / 5.7 / 8.0.x），binlog 格式虽兼容但无兜底 |
| Kafka + ZooKeeper | 16GB 内存的机器上，ZooKeeper 这 1 个容器和 512MB 内存是纯浪费，KRaft 是 3.x 的正式方案 |

## 4. 资源预算：16GB 怎么切

本机实测可用 15.7GB，这是整个项目**最硬的约束**，比 CPU 紧得多（7945HX 有 32 个逻辑核，用不完）。

WSL2 上限锁在 **10GB**（`.wslconfig` 的 `memory=10GB`），因此所有容器的内存 limit 之和压在 10GB 以内，剩下约 1.2GB 留给 WSL 内核与 dockerd。

| 容器 | 内存 limit | JVM 参数 | 说明 |
| --- | --- | --- | --- |
| `mysql` | 768 MB | 默认 | `innodb_buffer_pool_size=256M`，10 万订单量级够用 |
| `kafka` | 768 MB | `-Xmx512m` | 单节点 KRaft |
| `flink-jobmanager` | 768 MB | `-Xmx512m` | 只做协调，不承载状态 |
| `flink-taskmanager` | 2.5 GB | `-Xmx1536m` | 10 slots（9 个 CDC 作业 + 1 个埋点作业，并行度各 1），RocksDB 状态后端 |
| `doris-fe` | 1.5 GB | `-Xmx1g` | 元数据 + 查询规划 |
| `doris-be` | 2.5 GB | `mem_limit=70%` | 单 BE，建表统一 `replication_num=1` |
| **合计** | **8.75 GB** | | 余量约 1GB，够 dockerd 与内核 |

`kafka-ui`（256 MB）先不启用，用 `kafka-console-consumer.sh` 看 topic 与积压，省一个容器。

### 为什么不让 limit 之和超过上限

早期版本按 12.25GB 配（BE 4G、TM 3G），理由是「limit 是天花板，不是预留，空跑不会真占」。这个说法在通用场景成立，但对 Doris BE **不成立**：

- BE 的 `mem_limit` 是**软目标**而非硬阈值，它会一路吃到限制值
- Compaction 与大批量导入的内存尖峰，容易和 Flink Checkpoint 撞在同一时刻
- 触发 WSL 的 OOM Killer 时，被杀的不一定是吃内存最多的进程，可能是 Kafka 或 MySQL——现象表现为「Kafka 无故掉线」，排查成本极高

数据只有 121MB，给 BE 4GB 没有收益。宁可让每个容器紧一点，也别让宿主机开始 swap：swap 落在 D 盘的 vhdx 上，比内存慢两个数量级。

对应的 `.wslconfig` 基线：

```ini
[wsl2]
memory=10GB          # 留 5.7G 给 Windows
processors=8         # 32 核里给 8 核，再多宿主机会卡
swap=2GB
swapFile=D:\\wsl\\swap.vhdx

[experimental]
autoMemoryReclaim=gradual   # 空闲时把内存还给 Windows
sparseVhd=true             # 让 vhdx 能缩容，否则只增不减
```

全链路联调（六个容器同时跑作业）就用这套 8.75GB 配置，不再临时放宽 WSL 上限——改 `memory` 必须 `wsl --shutdown` 重启整台虚拟机，中途所有容器状态丢失，得不偿失。

## 5. 宿主机准备

### 5.1 磁盘落位（唯一的硬性风险）

实测 C 盘只剩 **33.8GB**，而 Docker 默认把 WSL 虚拟磁盘放在 `C:\Users\C\AppData\Local\Docker\wsl\`。四个服务的镜像解压后 8–12GB，加上数据持续写入，**vhdx 默认只增不减**，两周内必然写满 C 盘。

所以安装时必须做两件事：先建目录、再改 Docker Desktop 的 Disk image location。**顺序不能反**——先装后改会让 Docker 在 C 盘先落一份，改完还得手工搬。

```powershell
mkdir D:\Docker
mkdir D:\wsl
```

### 5.2 写 `.wslconfig`

文件位置 `C:\Users\C\.wslconfig`（当前不存在），内容见 §4。

### 5.3 安装 WSL2

**管理员** PowerShell：

```powershell
wsl --install --no-distribution
```

`--no-distribution` 是关键：Docker Desktop 会自己创建它需要的发行版，没必要额外装一个 Ubuntu 再占 2GB。需要 Linux 命令行时直接 `docker exec -it <容器> bash`。

装完**必须重启**。

### 5.4 安装 Docker Desktop

官网下载安装器，装完**先别急着跑容器**，立刻改三项设置：

| 位置 | 设置 | 不改的后果 |
| --- | --- | --- |
| Settings → Resources → Advanced | Disk image location → `D:\Docker\data` | C 盘被写满 |
| 同上 | CPUs = 8，Memory = 10GB，Swap = 2GB | Docker 认到 32 核后全放开，宿主机卡死 |
| Settings → Docker Engine | 加 `registry-mirrors` | 国内直连 Docker Hub 基本超时 |

```json
{
  "registry-mirrors": [
    "https://docker.m.daocloud.io",
    "https://dockerproxy.net"
  ]
}
```

### 5.5 通路验证（已完成，2026-10-30）

先别写 compose，用一个 MySQL 验证四件事：**能拉镜像、端口能映射、数据能持久化、binlog 事件正确**。

```powershell
$vol = '<仓库绝对路径>\docker\volumes\mysql'
docker run -d --name test-mysql `
  -p 3306:3306 `
  -e MYSQL_ROOT_PASSWORD=root123 `
  -e TZ=Asia/Shanghai `
  --memory 768m `
  -v "${vol}:/var/lib/mysql" `
  mysql:8.0.36 `
  --character-set-server=utf8mb4 `
  --collation-server=utf8mb4_unicode_ci `
  --binlog-format=ROW `
  --binlog-row-image=FULL `
  --server-id=1 `
  --innodb-buffer-pool-size=256M
```

> PowerShell 里写 `"$vol:/var/lib/mysql"` 会解析失败（`:` 被当成驱动器限定符），必须写 `"${vol}:..."`。

实测结果：

| 检查项 | 期望 | 实测 |
| --- | --- | --- |
| 镜像拉取 | 成功 | `mysql:8.0.36` / 839MB / 44 秒（走镜像源） |
| 端口映射 | 宿主机 3306 可连 | `TcpTestSucceeded = True` |
| 数据落盘 | Windows 目录出现文件 | `docker/volumes/mysql/` 下 180 个文件 |
| 重启后数据 | 仍可查询 | 重启容器后 `smoke.t1` 仍返回 `1 hello` |
| `binlog_format` / `binlog_row_image` | ROW / FULL | ROW / FULL，`log_bin=ON`，`server_id=1` |
| binlog 事件 | 出现 `Write_rows` | `Table_map` → `Write_rows` → `Xid` |
| 运行时内存 | ≤ 768MB | 370 MiB |

`Write_rows` 这一行是整个验证的重点：**Flink CDC 读的就是这个事件**。如果 binlog 记成 `STATEMENT` 格式，CDC 拿不到变更前后的行值，作业会「启动成功、日志无错、零数据」——最难查的一类故障。

另外这次顺带验证了一个有风险的点：**仓库路径含中文（`电商实时数仓项目`），bind mount 正常工作**，180 个文件确实写进了 Windows 目录。所以状态目录可以继续用 `docker/volumes/`，不需要挪到纯英文路径。

验证完 `docker rm -f test-mysql`，并清空 `docker/volumes/mysql/`，别占着 3306。

> Git Bash 里跑要注意：MSYS 会把 `D:\...` 改写成 `/d/...` 再传给 docker。要么用 PowerShell，要么加 `MSYS_NO_PATHCONV=1`。

## 6. 已知坑（按踩到的概率排序）

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| Flink 容器里连不上 Kafka | Kafka 只配了 `localhost:9092`，容器内的 localhost 是它自己 | broker 双 listener：`PLAINTEXT://kafka:9092`（容器内）+ `EXTERNAL://localhost:29092`（宿主机），`advertised.listeners` 两个都写。9092 不要映射到宿主机，否则宿主机客户端会拿到能连上但没数据的地址 |
| Doris BE 一直 `Alive: false` | FE/BE 用 `127.0.0.1` 互指，在 Windows 上被解析成 Docker 内部网络 | compose 里给固定网段 + 固定 IP，`FE_SERVERS` / `BE_ADDR` 都写 IP 不写 localhost |
| `docker compose down` 后数据全丢 | 数据写在容器可写层 | 所有状态目录必须 bind mount 到 `docker/volumes/`（已在 `.gitignore`） |
| MySQL 容器反复重启，日志只有一屏 `chown: changing ownership of '/load/...': Read-only file system`，mysqld 完全没启动 | MySQL 的 entrypoint 会解析 `mysqld --verbose --help`，把 `secure-file-priv` 指向的目录当作自己的目录去 `mkdir -p` + 递归 `chown`；挂成 `:ro` 时 chown 失败，而 entrypoint 头部是 `set -eo pipefail`，整个脚本直接退出 | 导入目录**不要**挂 `:ro`。报错里出现 `chown` 而没有任何 mysqld 日志，就是这个原因，不要往镜像或参数上找 |
| `docker exec 容器 /opt/kafka/bin/xxx.sh` 报 `exec: "D:/.../opt/kafka/bin/xxx.sh": no such file or directory` | Git Bash（MSYS）把以 `/` 开头的参数当成 UNIX 路径，自动改写成 Windows 路径再传给 docker | 命令前加 `export MSYS_NO_PATHCONV=1`，或把路径写成 `//opt/kafka/bin/xxx.sh`（双斜杠）。这和 `-v D:\...` 被反向改写是同一个机制的两个方向 |
| 提交作业报 `NoSuchMethodError` | Connector jar 与 Flink 次版本不匹配 | 回到 §1 核对三件套 jar 的版本号 |
| Doris 建表报副本数不足 | 单 BE 集群默认 `replication_num=3` | 建表统一 `replication_num=1`，DDL 里写死 |
| 中文乱码 | 容器默认 locale | MySQL 用 `--character-set-server=utf8mb4`，CSV 导入显式指定编码 |

## 7. 版本升级路径（留个后手）

如果后续要升到 Flink 1.20（比如面试要求），必须**成套**升，缺一不可：

| 组件 | 现在 | 升级目标 |
| --- | --- | --- |
| Flink | 1.18.1 | 1.20.x |
| Flink CDC | 3.2.1 | 3.3.x 或 3.4.x |
| Doris Flink Connector | 1.18-24.0.1 | `flink-doris-connector-1.20-26.x` |
| Kafka Connector | 3.1.0-1.18 | `3.4.0-1.20` |
| JDK | 11 | 11 或 17（1.20 起 17 才开始主流，但 Scala 包问题仍在，建议 11） |

升级后用同一批数据跑一遍 §6 的幂等验证用例，指标结果必须与升级前完全一致——这才是能写进简历的「版本升级无回归」。
