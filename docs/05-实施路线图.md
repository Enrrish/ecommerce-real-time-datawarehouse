## 2. 分阶段详解

### P0 设计冻结 ✅

**已完成**：`docs/01` 架构（双数据源、分层职责、双时间戳、幂等策略）、`docs/02` 分层模型（35 张表）、`docs/03` 指标口径（五类指标）、`docs/04` 版本矩阵、`docs/assets/dashboard.png` 视觉稿。

**为什么放在最前**：表结构和指标口径不动，后面每个容器才有明确用途。反过来做（先搭环境再想口径）是最常见的返工来源。

| --- | --- | --- |
| WSL2 运行时（3.0.3.0） | ✅ | MSI 离线安装，满足 Docker 要求的 ≥2.1.5 |
| Docker Desktop 4.97.0 | ✅ | 引擎 29.9.2，WSL2 后端 |
| 资源上限（`.wslconfig`） | ✅ | 实测 8 核 / 9.715 GiB，与 `memory=10GB` 吻合 |
| 镜像加速 | ✅ | 三个源生效，`alpine` 拉取成功（52s / 4MB） |
| 磁盘落位 | ✅ | 引擎数据在 `D:\Docker\DockerDesktopWSL` |

**验收**：`mysql:8.0.36` 能起、能连、重启容器数据还在、`binlog_format=ROW` + `binlog_row_image=FULL` 两项正确。

**最后一个条件不能省**：这两项配错，CDC 作业能启动、能提交、日志不报错，但一条变更都读不到——是整个项目最隐蔽的坑。

### P2 数据源与载荷 ⬜

- `sql/mysql/01-schema.sql`：9 张业务表，字段类型与 Olist CSV 对齐，主键与索引按查询模式设计
- `scripts/load_olist.py`：CSV → MySQL，处理日期空值、`\r\n`、编码
- `scripts/gen_user_events.py`：合成埋点日志（`page_view → add_cart → checkout → pay`），带 `event_id` 与 `event_time`，写 Kafka
- MySQL 参数：`binlog_format=ROW`、`binlog_row_image=FULL`、`utf8mb4`

**验收**：每张表 `COUNT(*)` 与 CSV 行数一致；`SHOW MASTER STATUS` 有正在写的 binlog；Kafka topic 能消费到埋点消息。

### P3 ODS 入湖 ⬜

- Flink SQL CDC 作业 ×9（每张业务表一个或合并为一个多源作业）
- Kafka → `ods_user_event` 作业
- ODS 附加 `op` / `ts_ms` / `dt` 三列

**验收**：在 MySQL `UPDATE` 一行，5 秒内 Doris 查到新值；`INSERT` / `DELETE` 同理（DELETE 表现为 `op=d`）。

**这一步是全项目的分水岭**：通了，后面都是 SQL 加工；不通，后面全是空转。

### P4 DWD 明细 ⬜

- `dwd_trade_order_detail`：订单 × 订单行 × 商品 × 卖家 × 支付 打宽（核心表）
- `dwd_user_event_clean`：去重 + 过滤机器人 + 清洗字段
- `dim_user_zip` / `dim_product_zip`：SCD2 拉链，`start_date` / `end_date` / `is_current`
- `dim_geo`：geolocation 去重（一个邮编多个坐标）

**验收**：宽表行数 = `olist_order_items` 行数（不是订单数）；同一 `customer_id` 有多次地址变更时，拉链表只有一个 `is_current=1`。

### P5 DWS 汇总 ⬜

6 张表：分钟交易概览、类目日汇总、卖家日汇总、地域日汇总、小时漏斗、支付方式日汇总。

- Watermark 延迟 30s，`allowed lateness` 5 分钟
- AGGREGATE 模型，`SUM` / `REPLACE` 写入时预聚合
- 迟到数据回写：整点补数作业修正前 N 小时

**验收**：同一批数据分别走实时链路与离线 SQL 重算，GMV / 订单数误差为 0。

### P6 ADS 与质量 ⬜

- 6 张应用表，口径按 `docs/03` 固化
- 脏数据注入：3% 重复 `event_id` + 5% 乱序 + 迟到 5 分钟
- 基线对比：干净数据跑一次，脏数据跑一次，指标必须一致

**验收**：重复率指标能如实反映注入的 3%，但 GMV 与干净基线完全一致——这才叫幂等，而不是「我保证了 exactly-once」。

### P7 大屏接入 ⬜

三屏九块，数据源从静态稿换成 `ads_*` 表。链路健康度面板要显示 P99 延迟、Kafka 积压、Checkpoint 耗时三个真实指标。

**验收**：改一行 MySQL，大屏 5 秒内数字变化。

### P8 交付 ⬜

- README 补真实截图与启动命令
- `scripts/demo.sh`：一条命令从零到有数据
- 简历话术与答辩问题清单（`docs/02` §5 已列 4 条，继续补）

## 3. 关键路径

```
P1 ──► P2 ──► P3 ──► P4 ──► P5 ──► P6 ──► P7
       └─ 建表 SQL 是所有后续作业的前提
```

**串行不可并行的原因**：P3 的 CDC 作业依赖 P2 的表结构；P4 的宽表依赖 ODS 真实数据；P5/P6 的聚合依赖 DWD 粒度正确。想并行只能拆「写文档」和「写 SQL」，因为 SQL 改一次就要重跑整条链路。

**可以提前做的**：P2 的 `01-schema.sql` 和 `scripts/gen_user_events.py` 不依赖 Docker，可以在等环境时先写。
