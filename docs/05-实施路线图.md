**验收结果（全部实测）**

| 项 | 结果 |
| --- | --- |
| 9 张 CDC 表行数与 MySQL 逐表 diff | **全 0**（含 geolocation 1,000,163 行） |
| `ods_user_event` 行数 | 22,004（Kafka 22,064 条消息，差值 60 = 注入的 3% 重复，唯一键吃干净） |
| 端到端延迟（UTC+8 宿主机掐表） | **3,849 ms**（MySQL 写入 → 轮询 Doris 至可见） |
| INSERT / UPDATE / DELETE | 全部同步正确；DELETE 后行从 ODS 消失 |
| 重跑快照幂等 | 重跑后行数仍为 99,441，未翻倍 |
| 漏斗 UV | 10,185 → 2,882 → 1,107 → 586，严格递减 |
| 埋点 join 商品维表 | 22,004 条全部命中，unmatched = 0 |

> **关于 DELETE 的验收口径要改**：原来写"DELETE 表现为 `op=d`"，但 UNIQUE 模型里
> `op='d'` 的那次变更会**把行删掉**，不可能留下一行 `op='d'`。所以正确的验收是
> 「DELETE 后该行从 ODS 消失」，删除痕迹留在 binlog 与 Kafka 里。这不是妥协，
> 是 UNIQUE 模型的语义（见 `docs/02 §1`）。要保留删除流水就得改 DUPLICATE 模型，
> 代价是每次重跑作业行数翻倍。

> **快照行的 `op` 是 `c` 不是 `r`**：Flink CDC 3.2.1 只暴露 `row_kind`（+I/+U/-U/-D），
> 没有 `op` 元数据，快照记录在 Flink 眼里就是 INSERT，只能映射成 `c`。
> 所以 `op` 无法区分「快照灌进来的历史」与「真实新增」，要区分只能看 `ts_ms`
> （快照行是哨兵值 0）。这条推翻了我最初的设计假设，`02-verify.sql` 检查 2 已同步。

> **`dt` 的口径被实测纠正过一次**：最初取 `DATE(op_ts)`，结果首轮全量后 99,441 行订单
> 全部落在 1970-01-01（快照阶段没有 binlog 事件，`op_ts` 是 epoch 0）。改成
> `CURRENT_DATE`（落地日期）后正常。这个坑不报错、只让数据静默错位 —— 一旦 DWD 按
> `dt` 做动态分区（`start=-30`），1970 分区会被当场 DROP，而 ODS 看起来"数据都在"。

**这一步是全项目的分水岭**：通了，后面都是 SQL 加工；不通，后面全是空转。

### P4 DWD 明细 ⬜

- `dwd_trade_order_detail`：订单 × 订单行 × 商品 × 卖家 × 支付 打宽（核心表）
- `dwd_user_event_clean`：去重 + 过滤机器人 + 清洗字段
- `dim_user_zip` / `dim_product_zip`：SCD2 拉链，`start_date` / `end_date` / `is_current`
- `dim_geo`：geolocation 去重（一个邮编多个坐标）

**验收**：宽表行数 = `olist_order_items` 行数（不是订单数）；同一 `customer_id` 有多次地址变更时，拉链表只有一个 `is_current=1`。

### P5 DWS 汇总 ⬜

6 张表：分钟交易概览、类目日汇总、卖家日汇总、地域日汇总、小时漏斗、支付方式日汇总。

- Watermark 延迟 30s，`allowed lateness` 5 分钟
- AGGREGATE 模型，`SUM` / `REPLACE` 写入时预聚合
- 迟到数据回写：整点补数作业修正前 N 小时

**验收**：同一批数据分别走实时链路与离线 SQL 重算，GMV / 订单数误差为 0。

### P6 ADS 与质量 ⬜

- 6 张应用表，口径按 `docs/03` 固化
- 脏数据注入：3% 重复 `event_id` + 5% 乱序 + 迟到 5 分钟
- 基线对比：干净数据跑一次，脏数据跑一次，指标必须一致

**验收**：重复率指标能如实反映注入的 3%，但 GMV 与干净基线完全一致——这才叫幂等，而不是「我保证了 exactly-once」。

**验收**：改一行 MySQL，大屏 5 秒内数字变化。

## 3. 关键路径

```
P1 ──► P2 ──► P3 ──► P4 ──► P5 ──► P6 ──► P7
       └─ 建表 SQL 是所有后续作业的前提
```

**串行不可并行的原因**：P3 的 CDC 作业依赖 P2 的表结构；P4 的宽表依赖 ODS 真实数据；P5/P6 的聚合依赖 DWD 粒度正确。想并行只能拆「写文档」和「写 SQL」，因为 SQL 改一次就要重跑整条链路。

**可以提前做的**：P2 的 `01-schema.sql` 和 `scripts/gen_user_events.py` 不依赖 Docker，可以在等环境时先写。
