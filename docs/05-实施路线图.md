> **关于 DELETE 的验收口径要改**：原来写"DELETE 表现为 `op=d`"，但 UNIQUE 模型里
> `op='d'` 的那次变更会**把行删掉**，不可能留下一行 `op='d'`。所以正确的验收是
> 「DELETE 后该行从 ODS 消失」，删除痕迹留在 binlog 与 Kafka 里。这不是妥协，
> 是 UNIQUE 模型的语义（见 `docs/02 §1`）。要保留删除流水就得改 DUPLICATE 模型，
> 代价是每次重跑作业行数翻倍。

> **快照行的 `op` 是 `c` 不是 `r`**：Flink CDC 3.2.1 只暴露 `row_kind`（+I/+U/-U/-D），
> 没有 `op` 元数据，快照记录在 Flink 眼里就是 INSERT，只能映射成 `c`。
> 所以 `op` 无法区分「快照灌进来的历史」与「真实新增」，要区分只能看 `ts_ms`
> （快照行是哨兵值 0）。这条推翻了我最初的设计假设，`02-verify.sql` 检查 2 已同步。

> **`dt` 的口径被实测纠正过一次**：最初取 `DATE(op_ts)`，结果首轮全量后 99,441 行订单
> 全部落在 1970-01-01（快照阶段没有 binlog 事件，`op_ts` 是 epoch 0）。改成
> `CURRENT_DATE`（落地日期）后正常。这个坑不报错、只让数据静默错位 —— 一旦 DWD 按
> `dt` 做动态分区（`start=-30`），1970 分区会被当场 DROP，而 ODS 看起来"数据都在"。

**这一步是全项目的分水岭**：通了，后面都是 SQL 加工；不通，后面全是空转。

### P4 DWD 明细 ✅

7 张表，分**两条路径**生成 —— 这是 P4 相对原设计唯一的调整：

**A. 两张流式表（Flink SQL 加工后写入 Doris）**

- `dwd_trade_order_detail`：订单 × 订单行 × 客户 × 商品 × 卖家 × 类目上 6 张表 CDC 直连 join，支付先按订单聚合
- `dwd_user_event_clean`：Kafka 埋点清洗，字段/白名单校验结果写进 `is_valid`（不物理删除，留证据）

**B. 五张维表（Doris 侧批处理 SQL，`sql/doris/04-dwd-load.sql`）**

- `dim_user_zip` / `dim_product_zip`：SCD2 拉链，`start_date` / `end_date` / `is_current`
- `dim_seller`：卖家维，全量覆盖（卖家属性无变更历史，不需要拉链）
- `dim_geo`：geolocation 去重（一个邮编多个坐标）
- `dim_date`：日历维，4,383 天（2016-01-01 ~ 2027-12-31），全层复用

**为什么维表不用 Flink 做 SCD2**：流式拉链在 Flink 里只有两条路 ——lookup join 或 `LAG` 窗口。
前者在 connector 24.0.1 上认证链路走不通；后者直接编译失败，因为 `LAG` 是 OVER 聚合，而 OVER 只能消费
append 流，CDC 输出带 `-U`/`+U` 是 changelog。既然维表数据是一次性加载的静态历史，用 Doris 的
`ROW_NUMBER()` 批处理更短、更好验证，也不占 Flink 状态。**不是所有东西都该流式做。**

### P5 DWS 汇总 ✅

6 张表，全部由 Flink SQL 从源端**直接聚合**写入 Doris。

> **为什么 DWS 不读 DWD 而是重算一遍 join**：DWD 已经物化到 Doris，而这个版本的
> Doris connector 没有流式 source，让 DWS 读 DWD 只能是批量读，那就退化成离线了。
> 代价是 MySQL 侧多几段 server-id、TM 多一份 join 状态；收益是 DWS 是真流计算。
> 风险是两边 SQL 漂移，所以验收必须用「DWS 汇总 == DWD 重算」硬核对。

**A. 两个必须自定的口径（原方案写的是"TUMBLE + Watermark 30s + lateness 5min"，实测不成立）**

- **时间轴取业务时间 `order_purchase_timestamp`，不是入湖时间**。两者差 8 年：
  订单时间跨 2016-09-04 ~ 2018-09-03（616 天），而 `update_time` 只有 7 个不同秒。
  取入湖时间会把 11 万行历史全塌进同一个分钟桶，大屏只剩一根柱子。
- **不用窗口，直接 GROUP BY 派生列做流式 upsert**。原方案在这套数据上必失败：
  埋点事件分两批、中间空 3 天，`allowed lateness 5 分钟` 接不住迟到 3 天的数据；
  只有一批数据时水位线推不到末尾，尾部窗口永不关闭 —— 正是 P4 踩过的
  「22,064 条只落 21,996 条」换个表再踩一遍。无窗口后迟到多久都能并进对应历史
  分桶，且每 key 每次下发**全量新值**，重放收敛，天然幂等。

**B. 表模型从 AGGREGATE 改成 UNIQUE KEY**

原方案定的是 AGGREGATE + `SUM` 写入时预聚合。这个选择有个没说破的前提：
**同一 key 的每一行只能导入一次**。而重放不是小概率事件 ——P4 单是调 connector
死锁就重跑了 7 次作业。AGGREGATE 的 `SUM` 列对此毫无防御，重放一次数字就翻倍。
改 UNIQUE（Merge-on-Write）后语义是「同主键保留最新一行」，配合 Flink 的
`SinkUpsertMaterializer`（Doris sink 声明 `ChangelogMode.upsert()`，Flink 会自动
插入这个算子把 retract 流归一化成全量更新），幂等性落在「值」上而不是写入协议上。
代价是失去写入时预聚合，但最大的表也只有 8.8 万行，ADS 在这个量级做 GROUP BY 是毫秒级。

**C. 一表一作业，不是一个作业装四张**

先按"单作业 STATEMENT SET 多 sink"实现，实测**子计划没有复用**：4 个 INSERT 的
SELECT 列表不同，投影裁剪给 4 份 join 生成了不同的输出行类型，`SubplanReuseExecutor`
认不出是同一棵树。结果是 35 个算子、22 个 Join（每条链 5.5 个），状态从 105MB
乘成 420MB，而每 slot 的 taskHeap 只有 217MB → TM 直接 OOM 退出、`slots-total` 归 0。

改成「一表一作业 + 每张表只 join 自己真正需要的维表」后单作业只有 40-90MB。
分钟表用不到商品/卖家/类目，砍掉这三个 CDC reader 既省资源也省 binlog 段。

**两个必须记住的口径事实**

1. **`order_cnt` 跨维度不可加**。一笔订单跨 3 个类目就在 3 个类目行各计一次：
   `overview`/`region` = 98,666（可加），`category` = 99,470，`seller` = 100,010，
   `payment` = 101,686。要总订单数只能查 DWD 的 `COUNT(DISTINCT order_id)`。
2. **支付金额 ≠ GMV**。`SUM(payment_value)` = 16,008,872.12 是支付流水口径；
   `SUM(item_total)` = 15,843,553.24 是商品+运费口径。差额 165,318.88 里混着
   775 个无明细订单的 830 笔支付（162,591.95），以及 Olist 原始数据里
   「支付金额 ≠ 商品金额 + 运费」的天然偏差 2,726.93。**不要相减算"误差"。**

| 一个作业装 4 张表，join 子计划因投影差异无法复用，状态 ×4 → TM OOM | 高 —— 作业状态是 `RESTARTING`，UI 只报 `NoResourceAvailableException`（招不到资源），真实死因 `OutOfMemoryError` 只在 `docker logs rt-flink-tm` 里；且 TM 死后集群 `slots-total` 归 0，容易误判成 scheduler 问题 |

**三处相对原设计的推翻：**

1. **`docs/03` 的 GMV 定义与实现差了 234 万，改文档向实现对齐。**
   原写「`SUM(price)` 不含运费、剔除取消单」= 13,494,400.74，而 P4/P5 一路用的是
   `SUM(item_total)` = 15,843,553.24。选实现口径的理由是流式语义：**取消是状态变更
   而不是行删除**，用 WHERE 过滤会让已计入的 GMV 凭空消失、累计曲线倒退。
   取消金额改由 `canceled_gmv`（108,026.21 / 0.68%）独立监控，净 GMV 用减法取。
2. **第六张表从 `ads_user_rfm` 换成 `ads_pipeline_health`。** Olist 复购率 3%，
   F 维度 97% 都是 1，分不出层。换成质量面板后，它成为整套方案里唯一能自证
   「实时」属性的材料。
3. **质量指标必须用「最近 N 条滑动窗口 + 跨分区均分」口径。** `dup_rate` 试了三次：
   全量口径 0.19%（被历史稀释 15 倍）、单分区窗口 1.27%（窗口大于注入批次）、
   三区各 1/3 才测出 2.9667%。累计口径会让质量指标越跑越「健康」，最终彻底失效。

**第七张表 `ads_region_map_1d` 是收尾补的（原「遗留问题」，已解决）。**

P6 做完六张表时发现 ADS 缺一张能被地图组件直接消费的表，而大屏有地图块。
选了补表而不是「让大屏直接查 DWS」—— 后者缺占比、缺名次、缺坐标，得让前端算，
等于把 SQL 挪到前端去写。

三件这张表独有的事：

1. **州中心坐标从 `dim_geo` 收敛，必须先过滤越界点。** `dim_geo` 19,015 行里有
   11 个坐标是错的（PA 一个点纬度跑到北纬 22 度、PR 的经纬度和经度串了位）。
   按巴西边界 `lat -34~6 / lng -74~-34` 过滤后再按 `point_cnt` 加权，27 个州的
   重心全部落位（SP -23.16/-47.08、AM -3.35/-60.54、RR 2.72 在北半球）。
   直接用 `AVG` 会把 PA 的重心拉到海里。
2. **地图填色必须用 `gmv_ratio` 而不是 `gmv`。** 各州差两个数量级，
   按绝对金额填色只有 SP 一州发红。
3. **地图永远有空白块。** 616 天里没有一天是 27 州全有成交（最多 26、平均 17.4）。
   北部 RR / AP / AC / RO 人口太少。这是数据特性，不是缺数。

顺带纠正了一个凭直觉下的错误结论：原本在字段注释里写 `buyer_cnt`「跨州可加」，
验证时发现有 **37 个自然人在两个州下过单**（占 95,420 名买家的 0.04%），
所以 `SUM(buyer_cnt)` = 97,734 比全期去重 95,420 大 2.4%。改成「任何跨桶相加
都会偏大」。教科书式的教训：**可加性不能凭直觉断言，得跑一次数据。**
