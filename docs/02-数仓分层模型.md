# 数仓分层模型

## 1. 表清单

### ODS —— 贴源层

| 表名 | 粒度 | 主键 | Doris 模型 | 来源 |
| --- | --- | --- | --- | --- |
| `ods_orders` | 订单当前态 | `order_id` | UNIQUE | CDC |
| `ods_order_items` | 订单行 | `order_id` + `order_item_id` | UNIQUE | CDC |
| `ods_order_payments` | 支付流水 | `order_id` + `payment_sequential` | UNIQUE | CDC |
| `ods_order_reviews` | 评价 | `review_id` + `order_id` | UNIQUE | CDC |
| `ods_customers` | 客户 | `customer_id` | UNIQUE | CDC |
| `ods_sellers` | 卖家 | `seller_id` | UNIQUE | CDC |
| `ods_products` | 商品 | `product_id` | UNIQUE | CDC |
| `ods_geolocation` | 邮编坐标 | `id`（自增代理键） | UNIQUE | CDC |
| `ods_category_translation` | 类目翻译 | `product_category_name` | UNIQUE | CDC |
| `ods_user_event` | 埋点事件 | `event_id` | UNIQUE | Kafka |

ODS 末尾追加元信息字段（**追加在末尾，不插在开头**，这样 Flink 的 `INSERT ... SELECT` 能按位置对齐源表前 N 列）：

| 字段 | 类型 | 含义 | 出现在 |
| --- | --- | --- | --- |
| `op` | `VARCHAR(1)` | `c` / `u` / `d`（由 Flink 的 `row_kind` 映射：`+I`→`c`、`+U`/`-U`→`u`、`-D`→`d`） | 9 张 CDC 表 |
| `ts_ms` | `BIGINT` | binlog 事件时间（毫秒）。**快照行是哨兵值 `0`**，表示"这一行没有源端时间戳" | 全部 10 张 |
| `dt` | `DATE` | **ODS 不分区**，此列仅作分析维度。9 张 CDC 表取 `CURRENT_DATE`（**落地日期**），`ods_user_event` 取 `DATE(event_time)`（**事件日期**） | 全部 10 张 |

> `ods_user_event` 没有 `op`：Kafka 消息里不存在「变更类型」这个概念，一条埋点就是一次新增。
> `op='d'` 在 UNIQUE 模型下会把行删掉，所以表里最终只会看到 `c/u`——删除痕迹在 binlog 与 Kafka 里，不在 ODS（见 §5.2）。
>
> **`dt` 在 ODS 和 DWD 的语义不同，这是有意的。** ODS 的 `dt` 回答「这行什么时候进湖」，
> 因此快照批量灌入时全部是落地日；DWD 的 `dt` 回答「这笔业务发生在哪天」，是分区裁剪的依据。
> 两者混用会出两类事故：拿 ODS 的 `dt` 做动态分区，历史数据全落在同一天，等于没分区；
> 拿 DWD 的 `dt` 判断新鲜度，则永远看不到今天的数据。详见 §3。

> **两条被实测推翻的初版设计**（P3 落地时发现，详见 `docs/05` P3 段）：
> 1. **`op` 没有 `r`**。原设计按 Debezium 约定写 `c/u/d/r`，但 Flink CDC 3.2.1 的
>    `mysql-cdc` 只暴露 `row_kind`（+I/+U/-U/-D），不提供 `op` 元数据。快照记录在
>    Flink 眼里就是 INSERT，只能映射成 `c`。后果：`op` 无法区分快照与真实新增。
> 2. **`dt` 不能取 `DATE(ts_ms)`**。快照阶段没有 binlog 事件，`op_ts` 是 epoch 0，
>    照此计算首轮全量后 155 万行全部落在 `1970-01-01`；一旦 DWD 按 `dt` 做动态分区
>    （`start=-30`），1970 分区会被当场 DROP，而 ODS 看起来"数据都在"。
>    改为 `CURRENT_DATE`（落地日期）后正常。

> **两处主键按实测数据修正**（写 `sql/mysql/01-schema.sql` 时全量扫描 9 个 CSV 得到）：
>
> 1. `review_id` **不唯一**：99,224 条评价里有 814 次重复，最多重复 3 次。若按单列做主键，
>    MySQL 建表后导入直接撞主键失败；即便 Doris 用 UNIQUE 模型自动合并，也会丢掉 814 条明细。
>    实测 `(review_id, order_id)` 组合零重复，故改为复合主键。
> 2. `geolocation` 的 `(zip_prefix, lat, lng)` **不是自然键**：1,000,163 行里只有 720,154 个
>    不同三元组，280,009 条重复，同一三元组最多重复 314 次（同一邮编下密集采样）。
>    因此源表加自增代理键 `id`，去重仍然放在 DWD 的 `dim_geo` 做。
>
> 附带的两个红利：`geolocation` 有了自增主键，Flink CDC 增量快照可以直接按主键切 chunk，
> 比无主键表快一个量级；`orders` 表因此也有了稳定的快照切分键。

### 埋点事件契约（Kafka `user_event`）

`scripts/gen_user_events.py` 生产的消息格式。字段少是刻意的——每个字段都有下游消费者，
没有消费者的字段不进契约（`device`、`referrer` 这类先不加，大屏没有对应面板）。

| 字段 | 类型 | 说明 | 谁在用 |
| --- | --- | --- | --- |
| `schema_version` | int | 当前为 `1`，用于将来演进 | ODS 解析分流 |
| `event_id` | string(uuid) | 全局唯一 | `ods_user_event` 的 Unique Key，幂等去重 |
| `event_time` | string | `YYYY-MM-DD HH:MM:SS.mmm`，Asia/Shanghai | 窗口归属、`dt` 分区、链路延迟 |
| `event_type` | string | `page_view` / `add_cart` / `checkout` / `pay` | 漏斗环节 |
| `user_id` | string | `customer_unique_id`（自然人口径，96,096 个） | 各环节 UV |
| `session_id` | string(uuid) | 会话标识，同时作为 Kafka message key | 归因到首日、分区内保序 |
| `product_id` | string | 取自 `olist_products` 的真实 ID | 与 `dim_product_zip` join（须带 `is_current=1`，否则一条商品会匹配多行） |
| `page_url` | string | 商详页 `/product/{id}`、`/checkout`、`/pay/result` | 排查 join 不上商品的个案 |

三条约定：

1. **`event_time` 不允许晚于生产时刻**。生成器会把越界的会话整体前移。违反这条的后果是
   Flink 把它当迟到数据丢掉，现象是「生产了几万条，漏斗只统计到一半」，且日志无报错。
2. **`user_id` 用 `customer_unique_id`，不是 `customer_id`**。后者与 `orders` 是 1:1 的订单级 ID，
   拿它算 UV 会把同一个人按订单数重复计数（99,441 vs 96,096）。
3. **漏斗按商品独立转化**。一次会话浏览 1~3 个商品，每个商品各自走 加购→提交→支付，
   而不是「整个会话只有一个状态」。这样才和 §3「同一用户同一商品分别计入各自环节」的口径一致。

实测分布（2 万条，`--seed 20261030`）：`page_view` 77.9% / `add_cart` 14.5% /
`checkout` 5.0% / `pay` 2.6%，支付转化率 3.36%。


### DWD —— 明细层

| 表名 | 粒度 | 主键 | Doris 模型 | 说明 |
| --- | --- | --- | --- | --- |
| `dwd_trade_order_detail` | 订单行 | `order_id` + `order_item_id` + `dt` | UNIQUE | 交易事实宽表，项目核心，112,650 行 |
| `dwd_user_event_clean` | 事件 | `event_id` + `dt` | UNIQUE | 清洗后行为明细，25,007 行（P6 注入后；2 条字段级脏数据标 `is_valid=0`） |
| `dim_user_zip` | 用户 | **`customer_unique_id`** + `start_date` | UNIQUE | SCD2 拉链 |
| `dim_product_zip` | 商品 | `product_id` + `start_date` | UNIQUE | SCD2 拉链 |
| `dim_seller` | 卖家 | `seller_id` | UNIQUE | 全量覆盖 |
| `dim_geo` | 邮编 | `zip_prefix` | UNIQUE | 去重后的坐标维表 |
| `dim_date` | 日历 | `dt` | UNIQUE | 公共维度，全层复用 |

> **`dim_user_zip` 的粒度必须用 `customer_unique_id`，不能用 `customer_id`。**
> 源数据里 `customer_id` 是**订单级**的：99,441 个 `customer_id` 对应 99,441 个订单，
> 与 `orders` 是 1:1。真正的人去重后只有 **96,096** 个（即 `customer_unique_id`）。
> 若按 `customer_id` 建 SCD2 拉链，每个客户只会在下单那一瞬间出现一次、再无变更，
> 拉链退化成一张订单快照表，复购率、RFM 全部失效。差的 3,345 就是复购人群。

> **`dwd_trade_order_detail` 是订单行粒度，订单数不能从它反推。**
> 源端 `orders` 有 99,441 行，其中 **775 个订单没有 `order_items`**
> （603 `unavailable` + 164 `canceled` + 5 `created` + 2 `invoiced` + 1 `shipped`），
> 它们对应的 830 笔支付、162,591.95 元也不会进宽表。
> 所以：GMV / 商品件数 / 履约时长从宽表算（15,843,553.24 是基准线）；
> **订单数、取消率、支付总额必须回到 `ods_orders` / `ods_order_payments` 取**，
> 用宽表算会系统性偏低。这是粒度决定的，不是数据质量问题。

> **`dwd_user_event_clean` 没有会话内序号列（试过，撤了）。**
> 用 `ROW_NUMBER() OVER (PARTITION BY session_id ORDER BY event_time)` 在流里算，
> 必须给 `event_time` 加 watermark，而水位线永远落后于最新数据 —— 实测 topic 尾部
> 最后 8 条支付事件卡在算子状态里出不来，22,064 条只落 21,996 条。
> 序号本质是「查询时排序」，`event_time` 精确到毫秒且不可变，DWS 直接
> `ORDER BY event_time` 就够，不需要在 DWD 固化一个会错的派生列。

### DWS —— 汇总层

| 表名 | 粒度 | 主键 | 行数 | 主要指标 |
| --- | --- | --- | --- | --- |
| `dws_trade_overview_1m` | 分钟 | `dt` + `minute` | 88,157 | GMV、订单数、支付用户数 |
| `dws_trade_category_1d` | 类目 / 日 | `dt` + `category` | 18,990 | 类目 GMV、订单数、卖家数 |
| `dws_trade_seller_1d` | 卖家 / 日 | `dt` + `seller_id` | 69,413 | 履约时效、延迟发货率 |
| `dws_trade_region_1d` | 州 / 日 | `dt` + `customer_state` | 10,701 | 地域 GMV、运费占比 |
| `dws_traffic_funnel_1h` | 小时 / 环节 | `dt` + `hour` + `step` | 16 | 各环节 PV / UV |
| `dws_payment_method_1d` | 支付方式 / 日 | `dt` + `payment_type` | 2,276 | 笔数、金额占比 |

> **DWS 全部改成 UNIQUE KEY，原定的 AGGREGATE 已弃用。**
> AGGREGATE 的 `SUM` 列有个没说破的前提：同一 key 的每一行只能导入一次。
> 而重放不是小概率事件 —— P4 单是调 connector 死锁就重跑了 7 次作业。
> 重放一次 `SUM` 列就翻倍，且 Doris 侧不会报任何错。
> 改成 UNIQUE（Merge-on-Write）后，配合 Flink 的 `SinkUpsertMaterializer`
> （Doris sink 声明 `ChangelogMode.upsert()`，Flink 会自动插入这个算子把
> retract 流归一化成"每 key 一条全量新值"），幂等性落在**值**上而不是写入协议上，
> 重放多少次都收敛到同一结果。代价是失去写入时预聚合，但最大的表 8.8 万行，
> ADS 在这个量级做 `GROUP BY` 是毫秒级 —— 用一份确定正确的数据换一个用不上的优化。
>
> **DWS 的 `order_cnt` 跨维度不可加。** 一笔订单跨 3 个类目就在 3 个类目行各计
> 一次。实测：`overview` / `region` = 98,666（可加），`category` = 99,470，
> `seller` = 100,010，`payment` = 101,686。要"总订单数"只能查 DWD 的
> `COUNT(DISTINCT order_id)`，或取 `overview_1m` / `region_1d`。

### ADS —— 应用层

| 表名 | 粒度 | 行数 | 服务对象 |
| --- | --- | --- | --- |
| `ads_realtime_overview` | 分钟 | 88,157 | 大屏 KPI 条 + 成交趋势 |
| `ads_category_rank_1d` | 类目 | 18,990 | 大屏品类排行 |
| `ads_funnel_1d` | 环节 | 8 | 大屏转化漏斗 |
| `ads_payment_method_1d` | 支付方式 | 2,276 | 大屏环形图 |
| `ads_order_stream` | 订单 | 98,666 | 大屏实时订单流水 |
| `ads_pipeline_health` | 指标 | 10 | 大屏链路健康度面板 |
| `ads_region_map_1d` | 州 / 日 | 10,701 | 大屏地域地图 |

> **第六张表从 `ads_user_rfm` 换成了 `ads_pipeline_health`（P6 决定）。**
> 原设计想做 RFM 分层报表，但本文档 §1 和 `docs/03 §4` 自己都写了
> 「Olist 复购率天然极低（约 3%）」—— F 维度 97% 的用户都是 1 次，
> 分不出层。一张没有区分度的表撑不起一个大屏面板，做出来只是为了显得完整。
>
> 换成链路健康度后，它同时满足三个条件：① `docs/03 §5` 已经定义了 10 个指标，
> 口径现成；② P6 的验收本来就是「重复率能否反映注入的 3%」，指标直接落在这张表上；
> ③ 这是整套方案里唯一能自证「实时」属性的材料 —— 别的地方说的实时都只是设计意图。
>
> **它是纵表（key-value）而不是宽表**，理由：指标单位和口径各异（ms / % / 元 / 条），
> 宽表得全用 DOUBLE 硬塞；指标会增删，纵表加一行就行，宽表要 ALTER；
> 大屏渲染是遍历卡片列表，纵表查出来直接喂给列表组件，不用按字段名分支。
>
> **第七张表是 `ads_region_map_1d`（P6 收尾补的）。**
> P6 做完六张表时发现一个缺口：ADS 里没有一张能被地图组件直接消费的表，
> 而大屏有地图块。当时的选项是「让大屏直接查 `dws_trade_region_1d`」或「补一张表」，
> 选了补表 —— DWS 不带占比、不带名次、不带坐标，让大屏去算等于让前端写 SQL。
>
> 这张表比别的 ADS 表多两类东西，都是地图专用：
> **① 州中心坐标**，从 `dim_geo`（19,015 个邮编前缀点）按 `point_cnt` 加权收敛，
> 并滤掉 11 个越界点（PA 有个点的纬度跑到北纬 22 度、PR 的经纬度串了位）；
> **② `state_name` 葡语全名**，因为不同地图图源的 key 不一样，有的用缩写 SP、
> 有的用全名 São Paulo，两列都给前端自己选。
>
> **`gmv_ratio` 是这张表最该用的列。** 各州 GMV 差两个数量级（SP 占 32%、
> RR 占 0.01%），按绝对金额填色只有 SP 一州发红、其余全白。
>
> **地图上永远有空白块**：616 天里没有任何一天是 27 个州全有成交
> （最多 26 个、平均 17.4 个），北部 RR / AP / AC / RO 人口太少。
> 这是数据特性不是缺数，排查时别往这上面找。
>
> **7 张表全部 UNIQUE KEY，「ADS 累计类用 AGGREGATE」这条原设计没有落地场景。**
> 设想中的累计指标（今日累计 GMV）必须以「截至该分钟的全量值」存储，前端要的是
> 曲线上每个点的绝对值；用 AGGREGATE 的 SUM 列存增量，每次重刷都会把上一次的
> 值再叠一遍。ADS 由 Doris 侧 `INSERT OVERWRITE` 整表重建，天然幂等，
> 比 AGGREGATE 更合适（详见 `sql/doris/07-ads.sql` 文件头）。

## 2. Doris 表模型选型理由

| 层 | 模型 | 原因 |
| --- | --- | --- |
| ODS / DWD / DWS / ADS | **UNIQUE KEY（Merge-on-Write）** | CDC 重放与乱序到达自动收敛到最新态，幂等不需要在 Flink 层手写 |
| ~~ADS（累计类）~~ | ~~AGGREGATE~~ | **本层没有用上。** 真正的累计值必须存「截至该时刻的全量值」而非增量，SUM 列会把每次重刷再叠一遍，见上方 ADS 说明 |
| `ods_geolocation` | **UNIQUE**（原定 DUPLICATE，已改） | 见下方修正说明 |

> **修正：`ods_geolocation` 从 DUPLICATE 改为 UNIQUE(`id`)。**
> 「允许重复」说的是自然键 `(zip, lat, lng)` 有 28 万条重复，但源表已有自增代理键，
> 1,000,163 行 `id` 全唯一，用 `UNIQUE(id)` 一行不丢。
> 而 DUPLICATE 的代价是**作业重跑一次行数就翻倍**（100 万 → 200 万），且没有任何报错，
> 只能靠 `COUNT(*)` 逐年核对才能发现。UNIQUE 重放任意次结果恒定。
> 10 张表统一 UNIQUE 还有个附带好处：P3 只有一种失败模式要排查。

## 3. 分区分桶规范

**这一节原来的写法（「统一按 `dt` 动态分区，`start=-30`，`end=7`」）是错的，会把 P3 直接做废。** 写 `sql/doris/01-ods.sql` 时发现两处硬伤：

1. **动态分区会自动回收历史分区。** `start=-30` 表示 30 天以前的分区被自动 DROP。而 Olist 业务数据是 2016-09 ~ 2018-10，全量快照灌进去时每个 `dt` 都早于 30 天前，分区刚建好就被回收。现象是「导入报成功、`COUNT(*)` 是 0」，日志里只有分区回收记录，看起来不像报错。
2. **UNIQUE 表的分区列会破坏唯一性。** UNIQUE 表要求分区列是 Key 列的子集，且唯一性只在单个 tablet（单分区）内保证。若分区列取「装载日期」这类**可变**列，同一 `order_id` 今天更新一次、明天再更新一次，会分别落在两个分区里，两次更新互不覆盖 → 同一订单出现两行，GMV 凭空变高，全程无报错。

因此按层分开定，核心原则是：**分区列必须不可变**。

| 层 | 分区 | 分桶 | 理由 |
| --- | --- | --- | --- |
| **ODS** | **不分区** | 按行数 1 / 4 / 8 | 155 万行不需要分区裁剪；UNIQUE 的可变分区列风险最不值得担 |
| **DWD 事实表** | `RANGE(dt)` 按**年**分区，静态建 | 8 | `dt` = 下单日期，业务上不可变；数据集中在 2016/2017/2018/2026，按年只需 5~6 个分区 |
| **DWD 维表** | 不分区 | 1~4 | 全量小表 |
| **DWS / ADS** | 按天 `dt`，可开动态分区 `start=-90` / `-30`，`end=7` | 4 | 只服务实时看板，天然没有 2016 年那种历史包袱 |

其他约定：

| 项 | 规范 |
| --- | --- |
| 分桶列 | 取**基数最高**的 Key 列（订单类用 `order_id`，不用 `order_item_id`），便于与订单表做 colocate join |
| 副本 | `replication_num=1`（单机演示，生产应为 3） |
| 索引 | 明细层按查询频率对 `category`、`seller_id` 建 BloomFilter / 倒排索引（P4 视实际慢查询再加，不预先堆） |

> 分桶数不是越多越好。千万行以内的表 BUCKETS 超过 16 只会增加元数据与文件句柄开销，不会提升查询性能。反过来，**单 BE 上 8 桶 × 10 张表 = 80 个 tablet**，每个 tablet 都有内存与文件句柄开销，这也是 ODS 小表只给 1 桶的原因。

## 4. 关键字段约定

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `price` / `freight` / `gmv` / `pay_amount` | `DECIMAL(18,2)` | 金额一律用 DECIMAL，禁止 FLOAT |
| `event_time` / `proc_time` | `DATETIME` | 双时间戳，见架构文档 |
| `dt` | `DATE` | **按层不同**：ODS 不分区，仅作分析维度（9 张 CDC 表取 `CURRENT_DATE` 落地日，`ods_user_event` 取 `DATE(event_time)` 事件日）；DWD 事实表首次成为**分区列**，取 `DATE(order_purchase_timestamp)` 这类不可变的业务日期 | 全部 |
| `order_status` | `VARCHAR(24)` | `created/approved/shipped/delivered/canceled/unavailable/...` |
| `is_late` | `TINYINT` | 送达晚于预计送达日期则为 1 |
| `*_zip_code_prefix` | `CHAR(5)` | **必须按字符串处理**：24.1% 的邮编以 `0` 开头（如 `09790`），转成整数会变 `9790`，之后 Join 静默丢数据且不报错 |
| 时间类字段 | `DATETIME` | 不用 `TIMESTAMP`：它会做时区换算且 2038 溢出，CDC 抽到 Doris 后时间会整体偏移 8 小时 |

## 5. 建模要点（答辩时会被问到的）

1. **DWD 的粒度是订单行还是订单？** 是订单行。因为一行对应一个卖家一个商品，履约和评价都按行归属；订单级指标在 DWS 层用 `COUNT(DISTINCT order_id)` 还原。
2. **为什么 ODS 用 Unique 而不是存变更流水？** 变更流水由 Kafka / binlog 归档承担；ODS 里保留当前态可以让下游 Join 简单，`op` + `ts_ms` 仍可追溯最后一次变更。
3. **SCD2 拉链表在 Doris 怎么实现？** 用 UNIQUE KEY(`id`, `start_date`)，维护 `start_date` / `end_date` / `is_current` 三列；新版本写入时先关闭旧版本的 `end_date`。
4. **`dim_geo` 为什么要单独做？** Olist 的 geolocation 一个邮编对应多个坐标点，直接 Join 会放大事实表行数，必须先去重成一对一维表。
5. **类目翻译表能 INNER JOIN 吗？** 不能。`products` 有 73 个类目，`category_translation` 只有 71 行，`pc_gamer` 和 `portateis_cozinha_e_preparadores_de_alimentos` 没有英文名。必须 `LEFT JOIN` + `COALESCE(英文名, 葡语名)`，否则这两类商品会整批消失。
   实测影响 13 个商品、24 条订单行、GMV 5,514.48。占比只有 0.02%，但**它不报错**——对账时少了几千块却查不出原因，比直接报错难处理得多。
6. **评价表为什么用复合主键？** 见 §1 的实测修正：`review_id` 有 814 次重复，单列做主键会在导入阶段直接失败。

## 6. 事故复盘：八个「不报错但不对」的坑

这一章是全项目最值钱的部分，也是简历上真正该写的东西——不是「搭建了实时数仓」（人人都有），
而是「三次面板全绿但实际不工作，每次都靠可观测性把它揪出来」。

每条都按 **现象 → 怎么发现的 → 根因 → 判据** 组织，面试时可以按这个顺序讲。

### 6.1 僵尸作业：RUNNING + checkpoint 正常 + lag 0，但一行不写

07（分钟概览）为了省快照时间配了 `scan.startup.mode = 'latest-offset'`。结果作业 RUNNING、
checkpoint 每 10 秒成功、Kafka lag 归零、健康度 10 项全 ok，**但 Doris 一行不写，持续 47 分钟**。

**根因**：join 两侧的状态只能来自数据流。不读快照就没有 orders 侧的任何一行，于是
order_items 的每条变更都被判成「订单不存在」丢掉。更隐蔽的是 UNIQUE 表「不写不丢」——
历史数据还在，大屏数字照常显示，所以没人发现它已经停了。

**发现**：改一行 MySQL，等 90 秒无变化。再看 Flink 算子计数：source 的 `numRecordsOut=2`
（确实收到了变更），`Join numRecordsOut=0`（全丢）。两个数一对就锁定了。

**判据**：**带 join 的 CDC 作业绝不能配 `latest-offset`**。成本重估：07 只读 4 张表约 41 万行
（不是整个 ODS 层的 155 万），`initial` 也就 1~2 分钟，不值得为此冒僵尸的风险。

### 6.2 毒消息：Kafka 只读追加 + 硬失败 = 永久停摆

ODS 作业每 10 秒重启一次，lag 从 0 涨到 54,194。

**根因**三层叠在一起：一条 `{}` 脏消息让 `event_id` 为 NULL；探针脚本的 `schema_version`
是字符串 `"1.0"` 而真实数据是 int；Doris 那张表上这列是 NOT NULL。

关键认知：**Kafka 只能追加、位点只能往前**。作业重启一千次也绕不过那条坏消息。
这和「数据库里可以 UPDATE 掉坏行」的心智完全不同——在 Kafka 里只能改代码或手工跳位点。

**修复**：`json.ignore-parse-errors=true` + `COALESCE(schema_version, 0)` +
`WHERE event_id IS NOT NULL AND event_time IS NOT NULL`，三层都要，少一层还会挂。修完 30 秒 lag 归零。

**判据**：lag **只涨不跌** + 作业周期性 RESTARTING，先翻 TM 日志的异常栈，不要先怀疑吞吐。

### 6.3 9p inode：BE 无限重启，而 `df -h` 看不出任何异常

BE 启动即退出，日志 `a broken disk is found` → `All disks are broken, exit.`，无限重启。

**根因**：BE 的 storage 原来 bind mount 到宿主机目录，Docker Desktop on Windows 把它导出成
9p 文件系统，`statvfs` 返回的 inode 是假数据：`f_files=999`、`f_ffree=-999001`——
**可用 inode 是负数**。Doris 启动时检查每块盘的可用性，判成「inode 用尽」。
`ignore_broken_disk=true` 救不了，因为它是「全部盘都坏」。

**排查入口是 `df -T`（看文件系统类型）和 `df -i`（看 inode），不是 `df -h`**——
容量那一项反而完全正常，盯着容量永远查不出来。

**修复**：改用命名卷 `rt-doris-be-data`，落在 WSL 的 ext4 上，`df -i` 有 6700 万个 inode。
7.56GB / 89,559 个文件迁了 20 分 44 秒，迁后 15 秒 healthy，七表行数逐表对平。

### 6.4 指标本身在骗人：MIN 口径，和恒为 0 的算子计数

两个例子，都出在「监控自己」。

- `pipeline_freshness_s` 取三张主表 `update_time` 的**最近者**。而 `ads_realtime_overview`
  每 60 秒被批刷重写、`update_time` 跟着刷新——只要 ADS 在刷，交易链停多久都是「0 秒新鲜」。
  僵尸作业就是在这 10 项全 ok 的健康度下活了 47 分钟。真正的存活证据是
  `overview_join_rows`（07 四源累计读取行数，当前 415,418）。
- Flink 的算子指标 `read-records` / `numRecordsIn` 是**缓存快照**。拿它判活时看到
  `numRecordsIn` 恒为 0，据此误判「07 空转」，查了 40 分钟。最后改一行 MySQL 看
  `SUM(gmv)` 变不变，才确认它一直是好的。

**判据**：判活只看目标表——`COUNT(*)` + `MAX(update_time)`，或改一行源端数据看数变不变。
不看算子指标，也不看任何 `MIN` 口径的聚合。

### 6.5 「没测到」不能报成「测到 0」

同一个错误在这个项目里踩了四次：

| 位置 | 错误形态 | 后果 |
| --- | --- | --- |
| `e2e_latency_ms` | `MSYS_NO_PATHCONV=1` 关掉路径翻译，python 打不开 `/d/...`，`FileNotFoundError` 被 `2>/dev/null` 吞掉 | 退回常量 3,849，人工跑正常、大屏跑降级 |
| `late_ratio` | 采样窗口混入 1 小时前的回填事件 | 注入 5% 报成 **66.67%** |
| `--skip-kafka` | 不采集却写 0 | 健康度显示「重复率 0%」 |
| 大屏今日成交 | CDC 还没到当天数据时显示 ¥0.00 | 看起来像「今天一单没卖」 |

**统一原则**：拿不到数据就明说是「未采集 / 暂无」，不要给一个看起来正常的 0。
验收脚本同理——`curl` 失败返回 `ERR` 再拿去和基线比"不相等"，接口全程 500 也能打印出
「可见 306ms」且 `exit 0`。必须 `curl -f` + 输出格式校验 + 失败不参与命中 + 连续失败判 FAIL。

### 6.6 Doris 写太频：不报错，只变慢

把 sink 的 `buffer-flush.interval` 设成 1 秒（想着「越快越好」），连跑 3 小时后
`dwd_user_event_clean` 单 tablet 积压 **4,434 个数据版本**，`dws_traffic_funnel_1h` **6,276 个**
（那张表里只有 56 行）。BE 内存顶到 2.25GB 后 compaction 停摆，`COUNT(*) GROUP BY`
从 60ms 退化到 **28 秒**——7.7 万行的表读不动。

每次 Stream Load 生成一个版本，1 秒一次 = 每秒一个版本。**它不报错，只是越来越慢**，
而且版本清不掉，只能 `TRUNCATE` + 从 Kafka 重放（77,948 条）。

现在 04/06/09 是 10 秒，07 是 1 秒（无数据流时不产生新版本）。底线：**导入频率不低于 10 秒**。

### 6.7 RocksDB 在 Docker Desktop on Windows 上卡死 checkpoint

checkpoint 一直不完成，CPU 只用了 2.3 秒，墙钟卡 5 分钟，栈停在 `RocksDB.put` 的 native 调用。

**根因**：RocksDB 的 native 写在这个文件系统上极慢。**修复**：`state.backend = 'hashmap'`。
状态量小（每作业并行度 1，只有位点和未提交 chunk）时完全够用，不必为「生产该用 RocksDB」
的教条付代价。

### 6.8 TM OOM 的真死因只在 `docker logs` 里

作业显示 RESTARTING，集群 `slots-total` 归 0，**Flink UI 的异常栈里看不到根因**。

**根因**：TM 的 taskHeap 按 slot 数**均分**。2304m 的 process.size 算出 868MB taskHeap，
÷4 = 217MB/slot。而 07 的四表 join 快照状态实测 134MB（checkpoint state_size
140,932,698 字节），占掉 62%，剩下的不够 checkpoint double buffer 申请 →
TM 整个被 cgroup OOM Kill，4 个算子全丢，join 永远卡 `initializing`，但作业状态还是 RUNNING。

**判定**：`docker inspect -f '{{.RestartCount}}' rt-flink-tm`，涨 1 就是它。

**修复**：process.size 2304m → 3072m（taskHeap **1489MB** / **372MB** per slot），
mem_limit 3328m；同时 BE 从 2560m 降到 1792m 等量让出，六容器合计仍是 8.75GB。
**降 slot 数比加内存总量对症**——它改的是切蛋糕的方式，不是蛋糕大小。

### 6.9 三个已知短板，以及怎么答

| 短板 | 老实的答法 |
| --- | --- |
| **没有单元测试**（1 万行零单测） | 不回避。正确性靠三件东西兜：ODS 九表逐表 diff 全 0、DWS 与 DWD 重算 diff 全 0、`late_ratio` 的正向对照（注入 290/2,117 报 13.6986%，证明分子分母都对）。**只验证「过滤后变 0」不算数，那可能只是把信号一起滤掉了。** |
| **单机、无调度** | ADS 刷新是 Python 线程定时。生产上会换成 DolphinScheduler / Airflow 编排，或者把 ADS 改成 Flink 作业；健康度采集也应该独立成外部任务（现在已经是旁路脚本，不挂在主链路上——主链路挂了指标也停，就永远发现不了挂）。 |
| **数据量小**（155 万行） | 不谈吞吐，谈**状态与内存的约束关系**：134MB 的 join 状态 × slot 均分 = 217MB 撑不住，这是规模无关的结构性问题；4,434 个数据版本导致读不动，也是规模无关的。 |
