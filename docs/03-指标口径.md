# 指标口径

> 所有指标以本文档为唯一口径来源。修改口径必须同步更新本文档与 `ads_*` 表字段注释。

## 1. 交易类

| 指标 | 英文 | 口径 | 计算层 |
| --- | --- | --- | --- |
| GMV | `gmv` | `SUM(item_total)` = `SUM(price + freight_value)`，**含运费**、**不剔除任何订单状态** | DWS / ADS |
| 无效交易金额 | `canceled_gmv` | `SUM(item_total) WHERE order_status IN ('canceled','unavailable')` | DWS / ADS |
| 净 GMV | `net_gmv` | `gmv - canceled_gmv`，**不落表**，查询时相减 | 查询时 |
| 支付金额 | `pay_amount` | `SUM(payment_value)`，从支付流水原始粒度算，**不经过订单行宽表**、不筛状态 | DWS / ADS |
| 支付订单数 | `pay_order_cnt` | `COUNT(DISTINCT order_id)`，有支付记录的订单 | DWS |
| 支付用户数 | `pay_user_cnt` | `COUNT(DISTINCT customer_unique_id)` | DWS |
| 客单价 AOV | `aov` | `gmv / order_cnt`，**分母为订单数而非订单行数** | ADS |
| 件单价 | `avg_item_price` | `gmv / item_cnt` | ADS |
| 运费占比 | `freight_ratio` | `SUM(freight_value) / SUM(item_total)` | DWS / ADS |

> **GMV 口径在 P6 修正过一次，改了三个地方，必须记住。**
>
> 本文档初版写的是「`SUM(price)`，不含运费，剔除 `canceled` / `unavailable`」。
> P6 做 ADS 时发现这个定义和 P4/P5 已经跑出来的实现差了 **234 万**：
>
> | 口径 | 金额 |
> | --- | --- |
> | `SUM(item_total)` 全量（**现在的实现**） | 15,843,553.24 |
> | `SUM(item_total)` 剔除 canceled + unavailable | 15,735,527.03 |
> | `SUM(price)` 全量（初版文档的写法） | 13,591,643.70 |
> | `SUM(price)` 剔除取消（初版文档的严格口径） | 13,494,400.74 |
>
> 最终选择向实现对齐，理由是**流式语义**而不是「改起来省事」：
>
> 1. **取消是状态变更，不是行删除。** 订单从 `approved` 走到 `canceled` 是一次
>    UPDATE。若用 `WHERE order_status NOT IN (...)` 过滤，已经计入 GMV 的金额
>    会在状态变更后**凭空消失**，累计曲线出现负增长。要正确实现就得在 Flink 侧
>    维护 retract 语义 + 下游可撤回聚合，成本和风险都远高于收益。
> 2. **GMV 是下单口径，不是成交流水。** 电商 BI 惯例里 GMV 统计「下单金额」，
>    成交额（实收）另有口径。取消率作为独立质量指标监控才是有信息量的做法。
> 3. **`net_gmv` 用减法得到，口径明确。** `gmv - canceled_gmv` 一步得出，比在
>    两个层各写一套过滤条件更不容易出错。
>
> 附带修正：`pay_amount` 原来写「仅统计已付款状态」，但实现是从 `ods_order_payments`
> 直接聚合、**不筛状态**。支付流水表本身只记录实际发生的支付，不存在「未付款的支付行」，
> 再筛一遍状态是多余且会漏数（`not_defined` 这类状态会被误杀）。已改为不筛。

## 2. 流量与转化类

| 指标 | 口径 | 计算层 |
| --- | --- | --- |
| 商详 PV | `COUNT(1)` where `event_type = 'page_view'` | DWS |
| 各环节 UV | `COUNT(DISTINCT user_id)`，按环节去重，按天粒度 | DWS |
| 支付转化率 | `支付 UV / 商详 PV UV` | ADS |
| 环节转化率 | `下一环节 UV / 上一环节 UV` | ADS |
| 加购率 | `add_cart UV / page_view UV` | ADS |
| 下单转化率 | `checkout UV / add_cart UV` | ADS |

### 归因规则（必须写死，否则数字对不上）

- **漏斗按天归因到首日**：一个 session 跨天时，全部环节计入 session 首个事件的日期
- **UV 按天去重**：日 UV ≠ 小时 UV 之和，任何跨粒度相加都会放大
- **事件类型优先级**：同一用户同一商品在同一天内同时有 `pay` 和 `page_view`，漏斗中分别计入各自环节，不去重合并

## 3. 履约类

| 指标 | 口径 |
| --- | --- |
| 履约时长 | `delivered_at - purchase_at`，单位小时 |
| 下单到发货 | `shipped_at - purchase_at` |
| 延迟发货率 | `COUNT(delivered_at > estimated_at) / COUNT(delivered_at IS NOT NULL)`，**分母剔除未送达** |
| 准时率 | `1 - 延迟发货率` |
| 平均评分 | `AVG(review_score)`，仅统计有评价的订单 |

> 常见错误：延迟发货率把未送达订单也算作分母，导致分母虚高、指标虚低。

## 4. 用户类

| 指标 | 口径 |
| --- | --- |
| 下单次数 | `COUNT(DISTINCT order_id)` per user |
| 复购率 | 窗口内下单 ≥ 2 次的用户数 / 窗口内下单用户数 |
| 首购时间 | `MIN(purchase_at)` per user |
| 新客 GMV | 首购发生在窗口内的用户的 GMV |
| RFM-R | `DATEDIFF(统计日, MAX(purchase_at))` |
| RFM-F | 窗口内下单次数 |
| RFM-M | 窗口内 GMV |

> Olist 中绝大多数用户只下单一次，复购率天然极低（约 3%）。这不是算错了，需要在报告里提前说明。

## 5. 链路与质量类

| 指标 | 口径 | 用途 |
| --- | --- | --- |
| 端到端延迟 | 源端写入时刻 → 目标表可查时刻，取 P99 | KPI 卡「链路 P99 延迟」 |
| 事件年龄 | `NOW() - event_time` | 排查位点重放与时钟错乱，**不是**端到端延迟 |
| 迟到比例 | `COUNT(lag > 60s) / COUNT(*)` | 数据质量监控 |
| 重复率 | `1 - COUNT(DISTINCT event_id) / COUNT(event_id)` | 验证幂等 |
| Kafka 积压 | consumer lag，取 topic 总和 | 大屏链路健康度 |
| Checkpoint 耗时 | 最近 N 次 checkpoint 的 P95 | 大屏链路健康度 |
| 交易链 join 行数 | 07 四个源表累计读取行数，应 ≥ 40 万 | **唯一能发现「作业 RUNNING 但一行不写」的指标** |

> **「端到端延迟」和「事件年龄」是两个指标，不能混用。**
> 前者是掐表量出来的（源端写一行，轮询目标表直到可见），反映管道性能；
> 后者是 `NOW() - event_time`，一段 SQL 就能算，但它把「事件在源端躺了多久」也算进去了。
> 埋点生成器刻意做了 1 小时回填，所以事件年龄天然是小时级，用它当延迟会得出
> 「延迟 60 小时」这种荒谬结论。大屏上要显示的必须是前者。
>
> 区分方法：CDC 的 9 张表有 `ts_ms` 哨兵值（快照行是 0），埋点表有真实 `event_time`。
> 算事件年龄时 CDC 表必须 `WHERE ts_ms > 0`，否则 1970 年的行会把平均值拉到几万天。

> **「端到端」也有两个，别把 10 秒和 1 分钟混着引用。**
>
> | 口径 | 实测 | 量的是什么 | 谁在用 |
> | --- | --- | --- | --- |
> | 链路延迟 | P50 5.0 s / P99 **10.0 s** | Kafka 写出 → Doris 表可查（`check_lag.py` 打探针） | 健康度面板 `e2e_latency_ms` |
> | 面板可见 | **17.3 s**（另一轮 60.7 s） | 改一行 MySQL → 大屏 KPI 数字变（`demo-change.sh`） | 演示 |
>
> 差的那部分不是 Flink 慢，是 `ads_realtime_overview` **60 秒一轮的批刷**：
> DWS 在 3.4 s 时就已经变了，ADS 要等下一个周期，撞在周期哪一头全看运气（10.7 s ~ 57 s）。
> 所以「大屏延迟一分钟」是批刷周期的函数，跟流处理性能无关 ——
> 想改就调 `dashboard/server/app.py` 里 full 档的 period，不是调并行度。

> **`pipeline_freshness_s` 是 MIN 口径，别拿它证明「每条链都在写」。**
> 三张主表的 `update_time` 取最近者，而 `ads_realtime_overview` 每 60 秒被批刷重写、
> `update_time` 跟着刷新 —— 只要 ADS 在刷，交易链停多久都看不出来。
> 2026-11-04 的僵尸作业就是这样在 10 项全 ok 的健康度下活了 47 分钟。
> 交易链的存活证据是 `overview_join_rows`。

### 实测基线

| 指标 | 实测值 | 测量方式 |
| --- | --- | --- |
| 端到端延迟 P50 / P95 / P99（Kafka→ODS） | **5,247 / 9,602 / 9,932 ms** | `scripts/check_lag.py`，200 条探针（P8） |
| 端到端延迟 P50 / P95 / P99（Kafka→DWD） | **5,132 / 9,661 / 10,035 ms** | 同上 |
| 端到端延迟（CDC 路径，历史单次） | 3,849 ms | P3 手工掐表，MySQL `INSERT` 后轮询 Doris |
| 面板可见延迟（改 MySQL → 大屏 KPI） | **17.3 s / 60.7 s 两轮**，其中 DWS 3.4 s / 1.5 s | `scripts/demo-change.sh`（P8） |
| 理论最差延迟 | ≈ 10 s | 等于 sink 的 `buffer-flush.interval` / checkpoint 间隔 |
| 埋点重复率（注入批次内） | 2.91%（60 / 2,062） | 目标 3%，唯一键去重后表里少 60 行 |
| ODS 行数与源端偏差 | 0 | 九表逐表 diff |

**P99 贴着 10,000ms 不是链路慢，是架构下限。** Doris Connector 靠时间触发落库
（`sink.buffer-flush.interval = 10s`），一条数据最多在 connector 里躺 10 秒才发出去 ——
P50 约 5 秒正是「到达时刻在 0~10 秒窗口里均匀分布」的中位数。

想把 P99 压到秒级只能改这个间隔，但 1 秒会把 Doris 版本打爆（实测 4,434 个版本、
`COUNT(*) GROUP BY` 退化到 28 秒，见 `docs/05 §4`）。所以阈值定的是 **<12s ok / <20s warn**，
不是凭感觉的 5s。

> 旧口径「P3 单次实测 3,849ms」已废弃：单次采样不是测量，是引用测量 —— 优化了它不动，
> 劣化了它也不动。`collect-pipeline-health.sh` 现在读 `check_lag.py` 落的
> `scripts/.latency.json`，读不到才退回那条历史基线，并在阈值说明里注明。

### P6 脏数据注入实测（2026-11-02，提交 `P6`）

注入方式：`python scripts/gen_user_events.py --events 3000 --dup-rate 0.03 --late-rate 0.05`
—— 3,000 条唯一事件 + 3% 重复 `event_id` + 5% 乱序到达（只改发送顺序、不改 `event_time`）。

| 观测项 | 注入前 | 注入后 | 结论 |
| --- | --- | --- | --- |
| Kafka topic 消息数 | 22,064 | 25,155（+3,091） | — |
| `ods_user_event` | 22,004 | 25,005（**+3,001**） | 唯一键去重，90 条重复被挡 |
| `dwd_user_event_clean` | 22,004 | 25,005（**+3,001**） | 同上 |
| `dws_traffic_funnel_1h` pv | 22,004 | 25,005（**+3,001**） | `ROW_NUMBER` 去重视图生效 |
| `ads_funnel_1d` pv | 22,004 | 25,005 | 刷新后一致 |
| 重放 370 行 `dwd_trade_order_detail` | 112,650 行 / 15,843,553.24 | 完全不变 | Doris UNIQUE 幂等 |

**三层都只增加 3,001 条，与唯一事件数严格相等** —— 这正是「注入 3% 重复但指标不变」
的证明。注意 DWS 漏斗是唯一一条不经过 DWD 去重的链路（直连 Kafka），它靠
`ROW_NUMBER() OVER (PARTITION BY event_id ORDER BY PROCTIME())` 兜底。

**监控指标能如实反映注入，但口径必须选对。** `ads_pipeline_health` 的 `dup_rate`
三次尝试才测准：

| 口径 | 测出值 | 为什么错 |
| --- | --- | --- |
| 全 topic 累计 | 0.19% | 60 条重复被 2 万条历史稀释 15 倍 |
| 单分区最近 3,000 条 | 1.27% | 窗口大于注入批次，混进 2,000 条旧数据 |
| **3 分区各取 1,000 条** | **2.9667%** | ✅ 窗口正好覆盖一次注入的规模 |

同理 `late_ratio` 从 0% → **5.1333%**。结论：**重复率 / 乱序率这类质量指标
必须用「最近 N 条滑动窗口 + 跨分区均分」口径**，用累计口径会越跑越"健康"，
最终彻底失效 —— 这是 P6 最值得写进简历的一条经验。

## 6. 口径变更记录

| 日期 | 指标 | 变更 | 原因 |
| --- | --- | --- | --- |
| 2026-10-29 | `gmv` | 确立为不含运费、剔除取消单 | 初版定义 |
| 2026-11-02 | 端到端延迟 | 从「`proc_time - event_time` 取 P99」改为「掐表量写入到可见」 | 原口径混入了事件在源端的滞留时间，埋点回填 1 小时会让它恒为小时级，不能代表管道性能 |
| 2026-11-02 | 事件年龄 | 新增为独立指标 | 承接原「延迟」口径里真正有用的部分：判断位点是否重放、时钟是否错乱 |
| 2026-11-02 | `gmv` | 从「`SUM(price)` 不含运费、剔除取消单」改为「`SUM(item_total)` 含运费、不剔除」 | 初版口径与 P4/P5 实现差 234 万；且取消是状态变更而非行删除，过滤会让累计 GMV 倒退。取消金额改由 `canceled_gmv` 独立监控，净 GMV 用减法取 |
| 2026-11-02 | `pay_amount` | 去掉「仅统计已付款状态」的限制 | 支付流水表只记录实际发生的支付，再筛状态是多余且会误杀 `not_defined` |
| 2026-11-02 | 重复率 / 乱序率 | 从累计口径改为「最近 N 条滑动窗口 + 跨分区均分」 | 累计口径被历史稀释（2.91% 测成 0.19%），质量指标会永远显示健康 |
