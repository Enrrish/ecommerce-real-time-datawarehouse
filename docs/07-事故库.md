# 事故库

> **本文件是全项目「踩过并修掉」的坑的唯一事实源。**
> 其他文档（`docs/02`、`04`、`05` 与 `docs/note/*`）提到这些事故时只引用 ID（`A1`~`A8`），
> 不再重述细节——同一个坑曾经在 5 篇文档里各写一版，数字和判据慢慢就漂了。

## 0. 怎么用

- 每条按 **现象 → 怎么发现的 → 根因 → 判据** 组织，答辩时按这个顺序讲即可。
- ID 固定，新增事故往后排（`A9`、`A10`…），**不改旧号**，否则引用会失效。
- 每条结尾的「判据」是**下次遇到同类现象时最先查什么**——比根因更有用，因为它能在 5 分钟内排除 90% 的错误方向。
- 这些事故的共同点：**不报错**。日志干净、面板全绿、作业 RUNNING，但数据不动或数字是错的。项目里所有可观测性设计（`overview_join_rows`、正向对照、`curl -f`）都是被它们逼出来的。

## A1 · 僵尸作业：RUNNING + checkpoint 正常 + lag 0，但一行不写

07（分钟概览）为了省快照时间配了 `scan.startup.mode = 'latest-offset'`。结果作业 RUNNING、
checkpoint 每 10 秒成功、Kafka lag 归零、健康度 10 项全 ok，**但 Doris 一行不写，持续 47 分钟**。

**根因**：join 两侧的状态只能来自数据流。不读快照就没有 orders 侧的任何一行，于是
order_items 的每条变更都被判成「订单不存在」丢掉。更隐蔽的是 UNIQUE 表「不写不丢」——
历史数据还在，大屏数字照常显示，所以没人发现它已经停了。

**发现**：改一行 MySQL，等 90 秒无变化。再看 Flink 算子计数：source 的 `numRecordsOut=2`
（确实收到了变更），`Join numRecordsOut=0`（全丢）。两个数一对就锁定了。

**判据**：**带 join 的 CDC 作业绝不能配 `latest-offset`**。成本重估：07 只读 4 张表约 41 万行
（不是整个 ODS 层的 155 万），`initial` 也就 1~2 分钟，不值得为此冒僵尸的风险。
修复后新增的第 11 项健康度指标 `overview_join_rows` 就是专门盯它的。

## A2 · 毒消息：Kafka 只读追加 + 硬失败 = 永久停摆

ODS 作业每 10 秒重启一次，lag 从 0 涨到 54,194。

**根因**三层叠在一起：一条 `{}` 脏消息让 `event_id` 为 NULL；探针脚本的 `schema_version`
是字符串 `"1.0"` 而真实数据是 int；Doris 那张表上这列是 NOT NULL。

关键认知：**Kafka 只能追加、位点只能往前**。作业重启一千次也绕不过那条坏消息。
这和「数据库里可以 UPDATE 掉坏行」的心智完全不同——在 Kafka 里只能改代码或手工跳位点。

**修复**：`json.ignore-parse-errors=true` + `COALESCE(schema_version, 0)` +
`WHERE event_id IS NOT NULL AND event_time IS NOT NULL`，三层都要，少一层还会挂。修完 30 秒 lag 归零。

**判据**：lag **只涨不跌** + 作业周期性 RESTARTING，先翻 TM 日志的异常栈，不要先怀疑吞吐。

## A3 · 9p inode：BE 无限重启，而 `df -h` 看不出任何异常

BE 启动即退出，日志 `a broken disk is found` → `All disks are broken, exit.`，无限重启。

**根因**：BE 的 storage 原来 bind mount 到宿主机目录，Docker Desktop on Windows 把它导出成
9p 文件系统，`statvfs` 返回的 inode 是假数据：`f_files=999`、`f_ffree=-999001`——
**可用 inode 是负数**。Doris 启动时检查每块盘的可用性，判成「inode 用尽」。
`ignore_broken_disk=true` 救不了，因为它是「全部盘都坏」。

**排查入口是 `df -T`（看文件系统类型）和 `df -i`（看 inode），不是 `df -h`**——
容量那一项反而完全正常，盯着容量永远查不出来。

**修复**：改用命名卷 `rt-doris-be-data`，落在 WSL 的 ext4 上，`df -i` 有 6700 万个 inode。
7.56GB / 89,559 个文件迁了 20 分 44 秒，迁后 15 秒 healthy，七表行数逐表对平。

## A4 · 指标本身在骗人：MIN 口径，和恒为 0 的算子计数

两个例子，都出在「监控自己」。

- `pipeline_freshness_s` 取三张主表 `update_time` 的**最近者**。而 `ads_realtime_overview`
  每 60 秒被批刷重写、`update_time` 跟着刷新——只要 ADS 在刷，交易链停多久都是「0 秒新鲜」。
  僵尸作业就是在这 10 项全 ok 的健康度下活了 47 分钟。真正的存活证据是
  `overview_join_rows`（07 四源累计读取行数，当前 415,418）。
- Flink 的算子指标 `read-records` / `numRecordsIn` 是**缓存快照**。拿它判活时看到
  `numRecordsIn` 恒为 0，据此误判「07 空转」，查了 40 分钟。最后改一行 MySQL 看
  `SUM(gmv)` 变不变，才确认它一直是好的。

**判据**：判活只看目标表——`COUNT(*)` + `MAX(update_time)`，或改一行源端数据看数变不变。
不看算子指标，也不看任何 `MIN` 口径的聚合。

## A5 · 「没测到」不能报成「测到 0」

同一个错误在这个项目里踩了四次：

| 位置 | 错误形态 | 后果 |
| --- | --- | --- |
| `e2e_latency_ms` | `MSYS_NO_PATHCONV=1` 关掉路径翻译，python 打不开 `/d/...`，`FileNotFoundError` 被 `2>/dev/null` 吞掉 | 退回常量 3,849，人工跑正常、大屏跑降级 |
| `late_ratio` | 采样窗口混入 1 小时前的回填事件 | 注入 5% 报成 **66.67%** |
| `--skip-kafka` | 不采集却写 0 | 健康度显示「重复率 0%」 |
| 大屏今日成交 | CDC 还没到当天数据时显示 ¥0.00 | 看起来像「今天一单没卖」 |

**统一原则**：拿不到数据就明说是「未采集 / 暂无」，不要给一个看起来正常的 0。
验收脚本同理——`curl` 失败返回 `ERR` 再拿去和基线比"不相等"，接口全程 500 也能打印出
「可见 306ms」且 `exit 0`。必须 `curl -f` + 输出格式校验 + 失败不参与命中 + 连续失败判 FAIL。

## A6 · Doris 写太频：不报错，只变慢

把 sink 的 `buffer-flush.interval` 设成 1 秒（想着「越快越好」），连跑 3 小时后
`dwd_user_event_clean` 单 tablet 积压 **4,434 个数据版本**，`dws_traffic_funnel_1h` **6,276 个**
（当时那张表里只有 56 行；P5 验收时是 16 行，2026-11-05 关停时 97 行）。BE 内存顶到 2.25GB 后
compaction 停摆，`COUNT(*) GROUP BY` 从 60ms 退化到 **28 秒**——7.7 万行的表读不动。

每次 Stream Load 生成一个版本，1 秒一次 = 每秒一个版本。**它不报错，只是越来越慢**，
而且版本清不掉，只能 `TRUNCATE` + 从 Kafka 重放（77,948 条）。

现在 04/06/09 是 10 秒，07 是 1 秒（无数据流时不产生新版本）。底线：**导入频率不低于 10 秒**。

## A7 · RocksDB 在 Docker Desktop on Windows 上卡死 checkpoint

checkpoint 一直不完成，CPU 只用了 2.3 秒，墙钟卡 5 分钟，栈停在 `RocksDB.put` 的 native 调用。

**根因**：RocksDB 的 native 写在这个文件系统上极慢。**修复**：`state.backend = 'hashmap'`。
状态量小（每作业并行度 1，只有位点和未提交 chunk）时完全够用，不必为「生产该用 RocksDB」
的教条付代价。

## A8 · TM OOM 的真死因只在 `docker logs` 里

作业显示 RESTARTING，集群 `slots-total` 归 0，**Flink UI 的异常栈里看不到根因**。

**根因**：TM 的 taskHeap 按 slot 数**均分**。2304m 的 process.size 算出 868MB taskHeap，
÷4 = 217MB/slot。而 07 的四表 join 快照状态实测 134MB（checkpoint state_size
140,932,698 字节），占掉 62%，剩下的不够 checkpoint double buffer 申请 →
TM 整个被 cgroup OOM Kill，4 个算子全丢，join 永远卡 `initializing`，但作业状态还是 RUNNING。

**判定**：`docker inspect -f '{{.RestartCount}}' rt-flink-tm`，涨 1 就是它。

**修复**：process.size 2304m → 3072m（taskHeap **1489MB** / **372MB** per slot），
mem_limit 3328m；同时 BE 从 2560m 降到 1792m 等量让出，六容器合计仍是 8.75GB。
**降 slot 数比加内存总量对症**——它改的是切蛋糕的方式，不是蛋糕大小。

## 2. 三个已知短板，以及怎么答

| 短板 | 老实的答法 |
| --- | --- |
| **没有单元测试**（1 万行零单测） | 不回避。正确性靠三件东西兜：ODS 九表逐表 diff 全 0、DWS 与 DWD 重算 diff 全 0、`late_ratio` 的正向对照（注入 290/2,117 报 13.6986%，证明分子分母都对）。**只验证「过滤后变 0」不算数，那可能只是把信号一起滤掉了。** |
| **单机、无调度** | ADS 刷新是 Python 线程定时。生产上会换成 DolphinScheduler / Airflow 编排，或者把 ADS 改成 Flink 作业；健康度采集也应该独立成外部任务（现在已经是旁路脚本，不挂在主链路上——主链路挂了指标也停，就永远发现不了挂）。 |
| **数据量小**（155 万行） | 不谈吞吐，谈**状态与内存的约束关系**：134MB 的 join 状态 × slot 均分 = 217MB 撑不住，这是规模无关的结构性问题；4,434 个数据版本导致读不动，也是规模无关的。 |
