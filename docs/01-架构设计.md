# 架构设计

## 1. 为什么是双数据源

单一数据源做不出真实数仓的样子：

| 数据源 | 承载的业务 | 技术通道 | 典型延迟 |
| --- | --- | --- | --- |
| MySQL 业务库 | 订单、支付、商品、卖家、评价 | Flink CDC（binlog） | 秒级 |
| 用户行为日志 | 浏览、搜索、加购、结算 | Kafka + Flink | 毫秒~秒级 |

两条链路在 DWD 层汇合，才能做出「行为 → 转化 → 成交 → 履约」的完整链路指标。

## 2. 分层职责

```
ODS  贴源，只做结构化和元信息补全，不做业务清洗
DWD  明细，去重 / 过滤 / 维表打宽 / 派生字段，粒度 = 业务最小单元
DWS  汇总，按 分钟 / 小时 / 日 预聚合，供 ADS 与自助分析复用
ADS  应用，面向具体看板与报表，指标口径在此固化
```

约束：

- **ODS / DWD / DWS 三层由 Flink SQL 作业加工后写入 Doris**，Doris 只承担存储与查询，不做层间加工
  （不建物化视图链、不跑 Doris 内部定时调度）。层间依赖的实现形式是「下游 Flink 作业读上游表」
- **ADS 是唯一例外**：不起 Flink 作业，由 Doris 侧 `INSERT OVERWRITE` 从 DWS / DWD 全量刷新
  （`sql/doris/08-ads-refresh.sql`；其中 `ads_funnel_1d` 读 `dwd_user_event_clean`，
  `ads_pipeline_health` 由 `scripts/collect-pipeline-health.sh` 写入）。4 个 slot 已被常驻作业占满，
  而 ADS 是整表可重建的小表，批刷新比再起一条增量流简单。代价是刷新延迟受调度档位约束，见 §7 末尾
- **跨层引用只允许自上而下单向依赖**，DWS 不直连 ODS
- ADS 的聚合一律走 DWS；唯一例外是漏斗 —— `ads_funnel_1d` 读清洗后的 `dwd_user_event_clean`
  （这条链路没有对应的 DWS 汇总粒度，DWS 侧只有小时级的 `dws_traffic_funnel_1h`）
- 维度表统一放 DWD，ODS 不再维护维表冗余

## 3. 时间语义（本项目最关键的约定）

每张明细表同时保留两个时间戳：

| 字段 | 含义 | 来源 | 用途 |
| --- | --- | --- | --- |
| `event_time` | 业务真实发生时间 | 业务字段 / 事件自带 | DWS 的分组聚合、分区归属 |
| `proc_time` | 进入数仓的时间 | `NOW()` / Kafka 消息时间 | 延迟监控、数据质量 |

由此可以推出两个指标，并且拿到大屏的「链路健康度」面板：

- `event_age = proc_time - event_time` → **事件年龄**，不是端到端延迟
- `迟到比例 = count(event_age > 阈值) / count(*)` → 数据质量

> **这两个不能混用。** 端到端延迟必须掐表量（源端写一行、轮询目标表直到可见），
> `proc_time - event_time` 把「事件在源端躺了多久」也算进去了 —— 埋点回填 1 小时，
> 它就会恒为小时级。口径与实测见 [docs/03](03-指标口径.md) §5。

如果只保留一个时间戳，迟到数据要么被静默丢弃，要么污染聚合结果且无法定位。

## 4. 幂等与一致性

| 环节 | 手段 |
| --- | --- |
| Kafka 生产 | 固定 `event_id`，允许重复发送，由下游去重 |
| ODS 落库 | Doris Unique Key（Merge-on-Write），同主键自动覆盖 |
| Flink Checkpoint | **10s** 间隔，`EXACTLY_ONCE`，状态后端 **hashmap**（compose 全局默认 rocksdb，5 个作业都用 `SET 'state.backend' = 'hashmap'` 覆盖掉了），落本地文件系统 |
| 写入 Doris | Flink Doris Connector 两阶段提交，Checkpoint 成功才提交事务 |
| 重放 | 支持按时间区间重跑，重跑结果与原结果一致（幂等验证用例） |

> Checkpoint 间隔就是**数据可见延迟的上限** —— Doris Connector 靠 checkpoint 触发 Stream Load 提交，间隔设太大表现为「作业 RUNNING 但 Doris 查不到数据」。设 10s 时链路 P99 约 **10 s**（口径与实测见 [docs/03](03-指标口径.md) §5）。代价是状态快照频率变高，本项目的状态量（4 个常驻作业、并行度各 1）完全吃得下。

> 简历上可以写的一句话：**「链路在模拟 3% 消息重复 + 5% 乱序 + 迟到 5 分钟的注入下，指标结果与无脏数据基线完全一致。」** 这比「保证了 exactly-once」有说服力得多。

## 5. 迟到数据与乱序

**本项目不用窗口，也不用 watermark。** 初版设计的「TUMBLE + 30s 水位线 + 5 分钟允许迟到 + 整点补数作业」
在这套数据上不成立，已被实测推翻：

- **Flink 侧**：DWS 直接 `GROUP BY` 业务时间派生列（`dt` / `hour` / `minute`）做流式 upsert，
  每个 key 每次下发**全量新值**。迟到多久都能并进对应的历史分桶，重放也收敛。
- **Doris 侧**：全部表是 UNIQUE KEY（Merge-on-Write），同主键覆盖，乱序与重放自动收敛到最新态。
- **没有补数作业**：ADS 走 `INSERT OVERWRITE` 整表重建，重跑一次就是一次补数，不需要另起兜底任务。

> 为什么放弃窗口：埋点分两批、中间空 3 天，`allowed lateness 5 分钟` 接不住迟到 3 天的数据；
> 只有一批数据时水位线推不到末尾，尾部窗口永不关闭 —— 实测 topic 尾部 8 条支付事件卡在算子状态里
> 出不来，22,064 条只落 21,996 条。细节见 [docs/02](02-数仓分层模型.md) §1（`dwd_user_event_clean` 没有会话内序号那段）
> 与 [docs/05](05-实施路线图.md) P5。

## 6. 资源预算（16GB 内存）

WSL2 上限锁在 **10GB**（见 [docs/04](04-环境搭建.md) §4），容器 limit 之和必须压在 10GB 以内。

| 组件 | 内存 limit | 说明 |
| --- | --- | --- |
| Doris FE | 1.5 GB | 单 FE，元数据 + 查询规划 |
| Doris BE | 1.75 GB | 单 BE，`replication_num=1`，内存预算按 cgroup × 0.9 自算 |
| Flink JobManager | 768 MB | 只做协调 |
| Flink TaskManager | 3.25 GB | **4 slots**（4 个常驻作业，各并行度 1），taskHeap 1489MB ÷ 4 = 372MB/slot |
| Kafka（KRaft） | 768 MB | 单节点，topic `user_event` 3 分区 |
| MySQL 8 | 768 MB | `innodb_buffer_pool_size=256M` |
| **合计** | **≈ 8.75 GB** | 余下约 1.2GB 给 WSL 内核与 dockerd |

> 数据量只有 121MB，大内存没有收益。压缩 limit 是为了避免宿主机 swap——swap 落在 D 盘 vhdx 上，比内存慢两个数量级。
>
> **TM 给 3.25GB 跑 4 个作业**，是这套配置里最紧的一处：taskHeap 按 slot 数均分，
> 1489MB ÷ 4 = 372MB 一个 slot。能成立的三个前提是——每个作业并行度都是 1、CDC 状态只有
> 位点与未提交的 chunk、状态后端用 hashmap（RocksDB 的 native 写入在 Docker Desktop on
> Windows 上慢到卡死 checkpoint，见 [docs/04](04-环境搭建.md) §6）。
>
> 早期版本配的是 **10 slots**（9 个 ODS CDC + 1 个埋点各占一个），每 slot 只有 87MB，
> 六表 join 的 DWD 作业一上就 OOM。后来 DWD 直连源端、不再读 ODS，8 个 CDC 作业随之停掉，
> slot 数才降到 4。**降 slot 数比加内存总量更对症**——它改的是切蛋糕的方式，不是蛋糕大小。
>
> 2026-11-04 又补了一步：4 slot × 217MB 仍然不够 07 的 join 状态（134MB），
> 所以 TM 从 2.5GB 提到 3.25GB（372MB/slot），同时 BE 从 2.5GB 降到 1.75GB 等量让出，
> **合计仍是 8.75GB**。依据是 BE 的活跃数据只有 406MB（9.6GB 卷里 9.1GB 是未清的 trash）。

### 启动顺序（分三类 profile，不要一次全起）

```bash
docker compose --profile source  up -d   # mysql + kafka
docker compose --profile compute up -d   # flink jm + tm
docker compose --profile olap    up -d   # doris fe + be
```

> 架构文档到这里不再改动。后续如果发现某一层的职责要调整（比如把维表下推到 DWS），

> 小表，用 Doris 侧 `INSERT OVERWRITE` 全量刷比再起一条增量流更简单。这是取舍不是妥协——
> 代价是刷新延迟受调度间隔约束（today 档 1s / funnel 档 2s / full 档 60s），换的是不占 slot。
