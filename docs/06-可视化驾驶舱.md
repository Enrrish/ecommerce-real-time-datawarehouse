# 06 · 可视化驾驶舱

> 这篇是**搭建说明**，配套一份高保真设计稿。
> 设计稿回答"长什么样"，这篇回答"每张图用哪张表、哪个字段、怎么在 FineBI 里点出来"。
>
> 设计稿：`电商实时数仓-经营驾驶舱`（Ardot，三个 1920×1080 画框：
> `P1 经营总览` / `P2 实时监控` / `P3 履约转化`）
>
> 稿子里所有数字都是**从 Doris 的 ADS 表查出来的真值**，不是占位符。
> 复刻完可以直接对数，对得上才算搭对。

---

## 1. 为什么是这三页

ADS 七张表不是随便摆的，它们各自回答一个问题：

| 表 | 回答的问题 | 落在哪页 |
| --- | --- | --- |
| `ads_realtime_overview` | 生意什么时候好、什么时候差 | P1 走势、P2 小时订单量 |
| `ads_order_stream` | 卖出去的单最后都到哪一步了 | P1 状态构成 |
| `ads_category_rank_1d` | 什么品类赚钱 | P1 品类 Top7、P3 品类客单价 |
| `ads_region_map_1d` | 钱从哪来 | P1 州 Top8、P3 州订单量 |
| `ads_payment_method_1d` | 钱怎么付的 | P3 支付方式 |
| `ads_funnel_1d` | 人从哪一步走掉了 | P3 转化漏斗 |
| `ads_pipeline_health` | **这条链路本身活着没有** | P2 全部 |

前六张答业务，最后一张答"你凭什么信这六张"。
所以 P2 不是可有可无的运维页——它是这份驾驶舱的**可信度背书**，
放在第二页而不是最后一页，是因为面试时"你怎么知道数据是对的"比"GMV 多少"更难答。

FineBI 的仪表板是绝对定位，没有栅格系统。落地办法：
**先在纸上按上面的数字算好每张卡的 X/Y/宽/高，再在 FineBI 里逐张填进去。**
不要让 FineBI 自动排列——它会把间距搞成 8 或 12，你后面想对齐得一张张拖。

**只用一种主色**。饼图、环形、条形全部同一个蓝紫，靠长度和位置区分，

### 2.3 字体

| 用途 | 字体 | 字号 |
| --- | --- | --- |
| 中文标题 | Noto Sans SC Medium/Bold | 14 |
| 中文正文 | Noto Sans SC Regular | 12 / 11 |

### 3.2 GMV 走势（面积图）

```sql
SELECT SUBSTRING(minute, 1, 2) AS h, SUM(gmv) AS gmv
FROM realtime_dw.ads_realtime_overview
GROUP BY SUBSTRING(minute, 1, 2)
ORDER BY h;
```

- **必须先按 `minute` 归并**：这张表同一分钟有多行（不同 `dt`），
  直接画会把 24 个点画成 80 多个点。
- 参考线：日均 660,148 = `SUM(gmv) ÷ 24`，用虚线，不要用柱子。

### 4.1 四个 KPI（全部来自 `ads_pipeline_health`）

| 卡片 | `metric_key` | 值 | 阈值 |
| --- | --- | --- | --- |
| 端到端延迟 P99 | `e2e_latency_ms` | 10,035 ms | < 12,000 ok / < 20,000 warn |
| 管道新鲜度 | `pipeline_freshness_s` | 47 s | < 300 ok / < 3,600 warn |

| Checkpoint P95 | `checkpoint_p95_ms` | 2,588 ms | < 5,000 ok / < 15,000 warn |

### 4.2 小时订单量（柱状图）

同 3.2 的 SQL，度量换 `SUM(order_cnt)`，峰值 16:00 共 6,628 单。
**低于日均 4,111 的柱子用淡色**（`#C7D2FE`），高于的用主色 —— 这比
"给柱子加渐变"有用，它一眼把 00–08 和 23 点标出来了。

### 4.3 Flink 作业与槽位（列表）

4 个作业 / 4 slots / 1 TaskManager（taskHeap 1,489MB）。
这一块 FineBI 里做不了（它查不到 Flink REST API），两个选择：

1. **写死成静态文本**（设计稿就是这么做的）—— 演示够用，但会过期
2. 用 `flink_jobs_running` 这一个指标 + 文字说明代替

不要为了"实时"去接 Flink REST，那需要一个额外的数据源类型，
收益远小于成本。

### 4.4 链路健康度表（11 行）

```sql
SELECT metric_group, metric_name, metric_value, metric_unit,
       metric_level, threshold_desc
FROM realtime_dw.ads_pipeline_health
ORDER BY metric_group, metric_key;
```

| 分组 | 指标 | 值 |
| --- | --- | --- |
| capacity | Checkpoint P95 | 2,588 ms |
| capacity | 运行中作业数 | 4 个 |
| capacity | Kafka 积压 | 0 条 |
| capacity | 交易链 join 行数 | 415,418 行 |
| delay | 端到端延迟 | 10,035 ms |
| delay | 管道新鲜度 | 47 s |
| quality | 无效交易金额 | ¥108,026.21 |
| quality | 无效交易占比 | 0.68% |
| quality | 事件重复率 | 0.00% |
| quality | 事件年龄 P99 | 0 s |
| quality | 事件乱序比例 | 0.00% |

**这一列里有两个指标会骗人，必须配文字说明**：

- `管道新鲜度` 是 **MIN 口径**——三张主表只要有一张在写就是 47s。
  它不能证明交易链在写。真正能证明的是 `overview_join_rows ≥ 40 万`。
- `事件年龄 P99 = 0` **不代表健康**，它代表近 10 分钟根本没有事件进来。
  0 是"没测到"，不是"测到 0"。

## 5. P3 履约转化 · 逐图清单

### 5.1 四个 KPI（`ads_funnel_1d`，UV 口径）

| 卡片 | 算法 | 值 |
| --- | --- | --- |
| 整体转化率 | 支付 UV 1,794 ÷ 浏览 UV 32,814 | 5.47% |
| 加购率 | 加购 UV 9,874 ÷ 浏览 UV 32,814 | 30.09% |
| 结算 → 支付 | 支付 UV 1,794 ÷ 结算 UV 3,727 | 48.14% |
| 支付金额 | `SUM(pay_amount)` | 16,008,872 |

**全部用 UV 不是 PV。** 同一批人反复浏览会把 PV 口径的转化率压得很低，
两种口径都对，但不能混着用——这张卡一旦和漏斗图口径不同，
面试官问一句"为什么这两个数不一样"就露馅了。

### 5.2 转化漏斗（4 步）

```sql
SELECT step, step_order, pv, uv, conv_rate_vs_prev, conv_rate_vs_first
FROM realtime_dw.ads_funnel_1d
WHERE dt = (SELECT MAX(dt) FROM realtime_dw.ads_funnel_1d)
ORDER BY step_order;
```

| 步骤 | PV | UV | 较上一步 |
| --- | --- | --- | --- |
| page_view 浏览 | 63,254 | 32,814 | — |
| add_cart 加购 | 11,307 | 9,874 | 30.09% |
| checkout 结算 | 3,793 | 3,727 | 37.75% |
| pay 支付 | 1,818 | 1,794 | 48.14% |

画法用**横向条形 + 底色轨道**，不用漏斗图。理由：
63,254 → 1,818 是 35 倍落差，漏斗图最后两段会细成一根线，
既点不中也看不出比例。`lib` 里加个浅底色轨道，观感不变但能读出"占了多少"。

> ⚠️ 这张表的埋点是**本项目自造的数据**，不是 Olist 原始订单。
> 设计稿的筛选栏右侧写了这句，落地时不要删掉——它避免把
> 自造漏斗当成真实业务结论去讲。

## 6. 口径红线（在这套图里会具体踩到的地方）

| 红线 | 踩法 | 后果 |
| --- | --- | --- |
| `cum_gmv` 不可 SUM | P1 走势图误把 `cum_gmv` 当度量 | 结果是总 GMV 的 **91.5 倍** |
| `gmv_ratio` 不可跨天 SUM | P1 州图直接 `SUM(gmv_ratio)` | 实测算出 **22,836%**，正确做法是 `SUM(gmv) ÷ 总 GMV` |
| `buyer_cnt` / `order_cnt` 跨维度不可加 | 把不同页的订单数相加 | 37 人跨州，四个维度四套口径，加起来必然偏大 |
| `ads_realtime_overview` 每分钟多行 | 直接画 `minute` 维度 | 24 个点变成 80 多个点，走势图变成锯齿 |
| 比率列 4 位小数 | 把 `*_ratio` 相加求"总和" | 相加不为 1，判据用 `ROUND(x,3)=1.000` |
| `is_late` 三态 | `WHERE is_late = 0` 当"没迟到" | 未妥投的单 `is_late` 是 NULL，被一起过滤掉了 |

## 7. 在 FineBI 里的搭建顺序

```
1. 数据连接（已完成，见 note/28）
   → 只勾 7 张 ads_* 表，模式选「直连」

2. 新建仪表板 → 尺寸设「自定义 1920 × 1080」
   → 不要用「自动」，否则换显示器会重排

3. 先摆空卡片，再填内容
   按 §2.1 的栅格把 5 个 KPI + 4 个图表框拖出来，对齐后再加图
   反过来做（先做图再排版）会反复返工

4. 逐张加组件
   每个组件选表 → 拖维度到横轴、度量到纵轴 → 设聚合方式
   条形图记得关掉「自动排序」，用 SQL 里 ORDER BY 的顺序

5. 统一格式
   数值保留 2 位、千分位；百分比字段用「百分比」格式而不是乘 100
   轴标签 10 号、卡片标题 14 Bold、正文 12

6. 加筛选器
   P1：时间范围 / 州 / 品类
   P2：时间范围 / 作业 / 指标分组
   P3：时间范围 / 支付方式 / 口径
   筛选器放在筛选栏，不要浮在卡片上

7. 三页用「仪表板跳转」串起来（顶栏三个页签）
```

## 9. 这套图讲什么

一句话版本：**"我搭了一条实时链路，并且能说清楚它什么时候在说谎。"**

如果只能留三页里的两张，留 P1 和 P2。
P1 证明你懂业务指标，P2 证明你懂自己搭的东西。
P3 是加分项——它证明你会从数据里问出决策问题（哪个品类该提客单价、
哪个州单量大但不赚钱）。
